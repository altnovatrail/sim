# CLAUDE.md — working rules for this repository

If `spec/RULES.md` does not exist, the `spec` submodule is not checked out and the rules imported below are missing: stop before any work and ask the author to run `git submodule update --init`.

## Your role

You are the architect of `sim`, a component of NovaTrail: the learner simulator, which measures learner-model and engine on virtual learners and never changes them, and which holds no data of live learners. The documents under `docs/`, but for the epic archives `docs/plan/`, are written for the session of Claude Code that builds and runs the component: write them so that it can act on them without asking what you meant. The bar they meet, and which texts are written for people instead, are in the shared rules below.

## The component

sim runs learner-model and engine on thousands of virtual learners of different populations (concepts 15 spec) and holds the criterion and the tolerance bands (architecture 3.9 spec). It is a gate in their CI: a change that worsens the criterion is not merged, and the criterion is written down before the first candidate runs (repositories 4 spec, architecture 3.8 spec). It imports both libraries at build time, and their CI takes it at an exact tag as a CI tool, so there is no cycle: the caller writes `go.work` on the fly (R103 spec; repositories 1 spec, repositories 3 spec). What is sim's own to decide is R05: the bands live here, in a gate file that also names the library commits they were recorded on, and the order of releases runs through a sim tag. The CI of modules runs it when anything the simulator reads from a package changes (architecture 3.10 spec, R103 spec). sim reads the module packages — their server part, the canonical view — through spec's types, without module-kit; it holds no data of live learners (architecture 3.10 spec, architecture 3.9 spec, R62 spec, R72 spec). It derives its virtual learners' seeds with spec's random generator, one for the whole platform, not with a scheme of its own (R27 spec, R59 spec). It belongs to stage 1, with learner-model and engine (repositories 2.1 spec), and it is modelled on standalone's simulator, `tools/learners` (architecture 3.9 spec).

Its card in spec is architecture 3.9 spec. The card is the summary and this repository's [docs/architecture.md](docs/architecture.md) is the detail: section 2 there lists what the card left to decide and how it was decided (R03–R05); section 3 is what the code builds.

## Documents

The documents under `docs/` are in English, but for the epic archives `docs/plan/`, which stay in Russian; RUN.md and `run/` are in English, but for the epic's description, table 1 and the bodies of tasks (R143 spec, R153 spec, R154 spec; R61). What `docs/decisions.md` quotes of the plan in Russian, the archives and other repositories' Russian texts stays Russian, in «…» (RULES.md, Hard rules). This repository cites its own sections and decisions without a suffix — `architecture 2`, `R03` — and spec's with the suffix "spec".

- [docs/architecture.md](docs/architecture.md) — the component: what it does and does not do, its data and links (section 1), what the card left to decide and how it was decided (section 2), and what the code builds (section 3).
- [docs/decisions.md](docs/decisions.md) — this repository's decision log, `R01`…: read it before proposing a change. Other repositories cite its entries as `R03 sim`.
- [docs/sources.md](docs/sources.md) — the records of external facts — a provider's terms, a library's documentation, a release read — each with its source, its date and its quote; a claim in another document cites its record, as `sources 1.1` (R143 spec). - [RUN.md](RUN.md) — the work plan, in epics: its rules, in its section Rules, and table 1 with the current epic's tasks, run one at a time. A done task's body and its gist sentence move to its epic's archive in `docs/plan/` at once (R19 spec, R153 spec).
- `run/` — the plan's other tables, each a file opening with its rules (R153 spec): the epics for later, [run/EPICS.md](run/EPICS.md); the questions to the author, [run/QUESTIONS.md](run/QUESTIONS.md); the technical debt, [run/DEBT.md](run/DEBT.md). ## Environment

Open the repository in VS Code and choose "Reopen in Container"; clone it with `--recurse-submodules`, or the container checks out `spec/` when it starts. Keep the clone in a folder named `sim`, as `git clone` names it: `.claude/settings.json` keeps spec's own CLAUDE.md and its rules, `spec/.claude/rules/`, out of this repository's sessions by that path. The container is spec's: Node.js, Go, buf and just, and the GitHub CLI and Claude Code on top, with gopls of the template's kind `go`. The tools of this repository's own code come with that code, at exact versions; how its container then differs from spec's is recorded as a decision, as R46 canvas-api did for canvas-api.

- `just -f spec/justfile docs-check-repo` checks the documents: that their links lead somewhere, that every section and number they cite — this repository's and spec's, against spec/ at its tag — exists, that the decision log runs without gaps, and the tables of RUN.md and `run/` (R32 spec), and that files, rules, decision entries, sections and rows keep within their budgets of size: spec's block `repository` of `spec/tools/docs-check/budgets.json`, with what this repository's `docs-budgets.json` names in its place — raising one is an edit of that file (R145 spec; measurements 2.1). A task that touches the documents ends with the check green.
- `.claude/settings.json` compacts a session at 400 thousand tokens, fetches no claude.ai connector, runs the hook `UserPromptSubmit` of `spec/tools/session/`, which stops a prompt that starts another task than the one the session has led and names `/clear`, since one task is one session (R143 spec). The plugin `gopls-lsp` of `spec/claude-plugins/` loads by the devcontainer, `CLAUDE_CODE_PLUGIN_DIRS` of its `containerEnv`, from this container's own path, in every session here (R143 spec; R60).
- **The checks of each part** are its rule, `.claude/rules/<part>.md`, with the part's files in its `paths`. Claude Code loads a rule only when the session reads or edits a file it matches, and CI runs every check on every pull request (R143 spec; measurements 1.5 spec): before changing a part, read its rule. `docs-check-repo` matches `paths` only against the files git lists, as CI has them, so a part whose files `.gitignore` keeps out of git has no rule, and what must hold for it stays in this file: here `runs/`, the files of the decisive runs, which nobody commits, since the same seeds give them again to the byte (R28, R33). The rules and their parts: [go](.claude/rules/go.md) — the Go code, `go.mod` and the rules of code; [gate](.claude/rules/gate.md) — the gate file, the paths, the decisive runs and the judgements; [ci](.claude/rules/ci.md) — CI, the release, the devcontainer and the justfile.
