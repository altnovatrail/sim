## 1. Purpose and bounds

**Does:**
- runs `learner-model` and `engine` on thousands of virtual learners of different populations: a virtual learner answers tasks, the learner model estimates its mastery of skills, the engine chooses what to give next (architecture 3.9 spec; concepts 11, 12 spec). In the platform's work `api` passes the graph and the evidence to the libraries (architecture 3.8 spec), and on the simulator `sim` itself does;
- measures what the platform promises about the learner model and the engine:
  - the success corridor: a task is solved with a probability from 0.70 to 0.85, with the target 0.775 (concepts 12 spec);
  - the cautious "mastered" (concepts 11 spec);
  - the same input gives the same output, and each choice has a reason code from the closed list `ReasonCode` ([contracts text](../spec/contracts/README.md), section 15; R100 spec; concepts 12 spec).

  In the first slice, on the graphs of all three modules (R41 spec): the engine holds the success corridor where there is a verdict, goes by the author's order where there is none (concepts 4 spec), does not get stuck and does not declare "mastered" too early (product 10 spec);
- holds the criterion by which a new rule is chosen, and the tolerance bands (architecture 3.9 spec). The criterion is written down before the first run of a candidate (architecture 3.8 spec; concepts 11 spec; R163 standalone);
- serves as a CI gate (architecture 3.9 spec; repositories 4 spec):
  - every change to `learner-model` or `engine` is run on the simulator, and a change that worsens the criterion is not merged (repositories 4 spec). How a library's CI takes the simulator is section 3.9 (R05), and Т-16 `spec` was closed by spec with the answer of `sim` — R103 spec (R06);
  - the CI of `modules` runs `sim` if what the simulator reads from a package has changed — `sim` decides this — on the package of the pull request (architecture 3.10 spec; R103 spec; R05). Before the first tag of `sim` there is no such gate, and the first tag runs the graphs already published (R76 spec; Т-16). There the gate holds invariants and thresholds, not bands (section 3.9; R05).

**Does not:**
- does not change the algorithms but only measures them (architecture 3.9 spec). The learner model is the business of `learner-model`, the choice of the next lesson or task that of `engine` (architecture 3.8 spec);
- holds no data of live learners (architecture 3.9 spec): no answers, no work, no logs of `api`. The virtual learners are synthetic, like any examples in NovaTrail's repositories (RULES.md, Hard rules);
- does not call AI: everything that calls a model is in `tutor`, and code computes the learner model and the choice (architecture 1 spec; R03 spec);
- does not read modules through `module-kit` and does not check them: it reads the packages by the types from `spec` (architecture 3.9 spec; R62 spec; repositories 2.1 spec), and `module-kit` checks a module (architecture 3.7 spec). Д59 and Д107 in table 4 of RUN.md `spec` said otherwise, and R103 spec called that an error of those rows (R06);
- does not work in the platform: it is a CI tool, not a part of the service (repositories 1, 2.1 spec).

**Data and links:**
- the data are module packages, pinned by version: from them come the skill graphs, the tasks and the lessons. `sim` reads the server part, `server.json` — the module's canonical view with the tier of each skill and the numbers of each instance of a template (R62 spec; [format text](../spec/format/README.md), section 25) — by the types `formatv0.CanonicalView` of the Go module `spec` (R72 spec), without `module-kit` (architecture 3.9 spec). The code takes the Go module `spec` at the same tag as the submodule: the module's version and the submodule move together, and the module `spec` is excluded from Dependabot `gomod` (R64 spec; Д46 in table 4 of RUN.md `spec`). It reads the packages in the same window of format versions as `module-kit`: while the format is v0, only the current version, which from `spec` v0.10.0 is 0.4 (R44, R111 spec; R32), and before it, from v0.9.0, was 0.3. At stage 1 the packages lie in the releases of `modules` (architecture 3.10 spec);
- `sim` passes the graph to both libraries in the types of `learner-model`: it sets them, and `engine` takes them from it, so the graph from a package is translated into one form, not two (R28 spec). A function of `learner-model` derives the bands where a skill is taught from the module's skills and task descriptions, and the description of a task is one for evidence and for a candidate task: the band, the difficulty from 1 to 5 within the band, the skills, the items with their answer slots (architecture 3.8 spec; R51 spec). For the engine a task template is one task, and the simulator chooses the instance by a seed with the same choice as the platform (R60 spec). To the engine the simulator also gives the pool of tasks, the lessons, the lesson runs, the closed attempts of tasks with a rubric and the summary of issues — for a skill, the time of its last issue, where the issue of a lesson is the issue of each of its skills, and, if the skill's last closed attempt was a probe or a repetition, its outcome as facts; for a module, the number of choices, of a task and of a lesson one each; for a task, the time when its solution last went to the device — as `api` gives them in the platform's work (architecture 3.8 spec; R107 spec; concepts 5, 12 spec; R104 spec). The simulator assembles the summary from its own choices and attempts, as `api` does from its records. It selects the pool and the lessons, as `api` does, by `age_categories` for the learner's age category: this is a filter of `api`, not an input of the engine (R107 spec);
- there are no data of live learners (architecture 3.9 spec);
- at build time it depends on `learner-model` and `engine` (repositories 2.1, 3 spec). The CI of these libraries takes `sim` by a tag — as a CI tool, not as a build dependency, so there is no cycle (repositories 1 spec; Т-16). The CI of `modules` also takes `sim` by an exact tag (repositories 2.1, 3 spec). The caller pins the tag and the SHA of the commit of `sim`, and `go.work` puts its code in place (section 3.9);
- the libraries get the time and the seed from outside (architecture 3.8 spec): on the simulator `sim` gives them. `spec` sets the generator of randomness and the derivation of seeds, with test vectors — one for the whole platform: `module-kit`, widgets, `engine` and `sim` (architecture 1 spec; R27 spec). With it `sim` derives the seeds of virtual learners, not with a scheme of its own (architecture 3.9 spec), and it passes its test vectors in CI, with a workflow of its own (architecture 3.2 .github). The generator is PCG, and the stream of a place of randomness is derived by FNV-1a 64 from the seed and the names of the place (R59 spec; [format text](../spec/format/README.md), section 22). The function `seeded` of standalone's simulator is a particular case of this derivation, so the simulator's numbers are kept, and the normal and exponential distributions are not in the format, and `sim` is responsible for their portability (architecture 3.9 spec);
- the example is `tools/learners` and `docs/learners.md` in standalone (architecture 3.9 spec; sources 1.1–1.3). MathTrail's code under MIT is carried over freely, and the MIT notice is kept (R12 spec);
- the CI checks came before the code: the shared checks from `.github`, `docs-check-repo` among them, were connected by T21 of `spec`. Which they are and what holds the merge is R30 spec and architecture 3.11 spec. The checks of the language came with the first code of `sim`, the frame of T10 (repositories 1 spec; R10): the job "Go" of the shared `go.yml` with the input `same-bits` (R09), CodeQL for Go (Д9 in table 4 of RUN.md `spec`) and the tests, whose coverage goes to Codecov and holds the merge (R48 spec; RULES.md, How we work);
- stage 1, together with `learner-model` and `engine`: the simulator needs both the model and the rule of choice, and the simulator and the criterion appear before the first candidate (repositories 6 spec; product 11 spec).

### 2.1. Profiles of virtual learners

- **Gist:** which virtual learners the simulator has — how each answers, how its mastery of skills changes, how it studies over time — and on which skill graphs it goes. A population is an assumption about live learners: the simulator does not measure it but takes it, and what the criterion can see at all depends on the set of populations. Decided here: these are items of the card — the profiles of virtual learners, in this document the populations (section 3.1) — and forgetting, the weights of evidence and the anchor skill (architecture 3.9 spec).
- **What is known:**
  - in standalone the virtual learners are synthetic children of grades 1–6, each from its own seed, and the same children go through every rule. There are nineteen generators, and each changes one assumption of the base population: G0 stays put, G1 is placed a level off, G2 learns fast, G3 makes a jump, and so on. The main one is G2-half, a learner with the speed that MathTrail's author takes as plausible. Each child gives 200 answers, and every tenth answer starts a new day (sources 1.1);
  - there too: "How fast real children learn is not known: the speeds are the bench's, not a measurement" (sources 1.1);
  - a learner of NovaTrail is of any age, and the first slice has three modules of two subjects: olympiad maths for grades 1–6 on a handwriting sheet, grade 3 maths on a workbook and short essays in English for any age, with feedback by a rubric, not a verdict (R41 spec; О-1 decided; product 10 spec). The populations are children with a sheet and with a workbook and a learner of any age with essays (Д18 in table 4 of RUN.md `spec`). There are no language modules in the first slice, and the simulator checks forgetting on the two maths (architecture 3.9 spec). The populations of standalone are only children and only maths;
  - NovaTrail's learner model and engine do what was not done in standalone, and the populations must touch it. What the detailing of `learner-model` decided is in the card 3.8 spec, and the detailing of `engine` is still going on:
    - forgetting is the retention of a skill: without practice the retention fades, and with it the probability of a correct answer, and spaced practice grows the stability. Time does not take "mastered" away but gives a review date; the law and the constants are one for all modules (R04 learner-model). In standalone there was no forgetting. The libraries get the time from outside (architecture 3.8 spec), so a virtual learner has days, sessions and breaks, and it forgets by laws other than the model's law; there are learners who do not forget and learners whose level falls after a break (architecture 3.9 spec). When to give a skill whose review date has come is the repetition rule of `engine`, not yet decided (architecture 3.8 spec);
    - prerequisites: a skill is offered when its prerequisites are mastered, and a prerequisite from another module is an anchor skill (concepts 4, 12 spec; R50 spec). Whether the learner knows an anchor skill `learner-model` decides by the skills that teach it, in the learner's modules (R07 learner-model): among the populations, a learner with both maths (architecture 3.9 spec). The rule of standalone did not read the links between topics;
    - the level is per module, on the scale of that module's bands, and a skill has an offset (R03 learner-model): the populations have no variant "per area", and a learner of two modules has two levels (Д82 in table 4 of RUN.md `spec`);
    - guessing is per item, by its answer slots: for a choice, 1/k by the number of the answer slot's options, for a free answer, about zero (R03 learner-model; concepts 11 spec). In standalone it was hard-coded as 0.2;
    - the weights of evidence: the item's first verdict goes into the step, help does not let "mastered" be set, and each of the N answers of one attempt weighs 1/(1 + (N − 1)/3); repeating a task whose solution has already gone to the device is help (R06 learner-model). The populations have pages of a workbook where the answers depend on one another by a law other than the model's discount, an error that the learner repeats on the whole page, a day when everything goes worse, with hints, a technique on request and repeated tasks (architecture 3.9 spec; Д86 in table 4 of RUN.md `spec`);
    - lessons and essays: a learner takes a lesson as a lesson run, and an attempt of a task with a rubric gives no evidence, and the engine gets such closed attempts separately (architecture 3.8 spec; concepts 5 spec). A virtual learner goes through lessons and writes essays, since they are among the engine's inputs (Д83 in table 4 of RUN.md `spec`);
  - the simulator's tasks come from module packages (architecture 3.9 spec). A task's hardness is by its band and its difficulty from 1 to 5 within the band, and the scale of bands is in the module manifest (R51 spec; concepts 6 spec). A task template gives instances by a seed (R60 spec). In standalone a chat model wrote the task, and the generators set its miss — how much harder or easier the task truly is than the one asked for (sources 1.1);
  - the virtual learners are synthetic, and the simulator has no data of live learners (architecture 3.9 spec; RULES.md, Hard rules);
  - the seeds of virtual learners are derived by `spec`'s generator and derivation of seeds, one for the whole platform, and the simulator has no scheme of its own (R27 spec). The generator is decided — PCG and FNV-1a 64 (R59 spec; Т-18 closed) — and the function `seeded` of standalone's simulator in `tools/learners/child.go` is a particular case of it: the place of the main seed with the names "experiment, unit, assignment", so the simulator's numbers are kept (architecture 3.9 spec). How the working and held-out sets of learners do not overlap (R163 standalone) was T01's to decide, and R03 decided it (section 3.4);
  - the module format 0.3 and the package are decided (R44, R62, R101 spec), and there are no module packages yet: `modules` writes the first batch, and it has no release yet ([COORDINATION.md](../spec/COORDINATION.md), row 3.6).
- **Decided:** R03, 2026-11-07, by the author's answers in the planning of T01 and the proposals of the execution. The virtual learner and its calendar are section 3.1, the populations from standalone and the new ones 3.2, the graphs and tasks 3.3, the seeds 3.4. The card's profiles are the populations here: in `spec`'s vocabulary a profile is a learner in an account (section 3.1). Since v0.9.5 the card and the vocabulary both say so: "virtual learner" and "population" (concepts 15 spec; R103 spec; R06).
- **Deferred:** checking the simulator's numbers against live learners, until stage 2, when `api` has the data of live learners (Д3 in table 4, [DEBT.md](../DEBT.md)). The speeds, laws and shares of the populations are the simulator's assumptions, not a measurement, and are revised with that check.
- **Task:** T01, done.

### 2.2. The criterion and the tolerance bands

- **Gist:** by what rule a new rule of the learner model or of the engine is found better than the previous one, or at least no worse — this is the criterion — and how far the numbers may shift on each change for the CI gate to let it through — these are the tolerance bands. They must be written down before the first run of a candidate (R163 standalone): otherwise the candidate's numbers would affect what it is judged by. Decided here: this is an item of the card, and the measures of forgetting, of the weights of evidence and of knowing an anchor skill are also parts of three of its other items (architecture 3.9 spec).
- **What is known:**
  - every change to `learner-model` and `engine` passes the simulator by a criterion written down before the first run of a candidate, and a change that worsens the criterion is not merged (architecture 3.8 spec; repositories 4 spec; concepts 11 spec);
  - what the simulator must show in the first slice: on the graphs of all three modules the engine holds the success corridor, does not get stuck and does not declare "mastered" too early (product 10 spec). The corridor is from 0.70 to 0.85, with the target 0.775 (concepts 12 spec); "mastered" is a cautious estimate (concepts 11 spec); the simulator checks reproducibility and the reason code of each choice (concepts 12 spec). The list of reason codes is a contract in `spec`, the closed enumeration `ReasonCode` of eight values without parameters ([contracts text](../spec/contracts/README.md), section 15; R29, R100 spec). There are three graphs, and where there is no verdict — for skills with a rubric — the engine goes by the author's order, not by the corridor (product 10 spec; concepts 4 spec);
  - the success corridor is a rule of `engine`, and `learner-model` gives the probability of a correct answer (R23 spec; concepts 11 spec). The threshold "mastered" is a constant of `learner-model`, and a new target of the corridor is a new constant of the model, and both changes pass `sim` in one run (the 2026-11-02 amendment to R23 spec; architecture 3.8 spec). This is an input of the question whether there is one criterion for both libraries;
  - the measures that the card names as proposals of `learner-model` (architecture 3.9 spec; Д82 in table 4 of RUN.md `spec`) are an input of T02, not its decision:
    - forgetting: the calibration of the probability by the length of the pause, how many answers the model takes to catch up with a true fall, the share of repetitions over time, false "mastered" after a break, and on learners who do not forget, the model with forgetting is no worse than the model without it (architecture 3.2 learner-model);
    - the weights of evidence: false and early "mastered" from one or two pages, the calibration of the probability on pages and on answers with help, the shift of the estimate after a repeated task (R06 learner-model);
    - the anchor skill: the measure of a false "knows" (R07 learner-model);
  - in standalone these are two different mechanisms (sources 1.1):
    - **the criterion** chooses a new rule. It has constraints, the score, the choice among candidates, the confirmation on the held-out seeds and the exit if no candidate has passed. The score of the rating step is the share of the path from the rule in force to the "oracle", which knows where the child truly is; for the rule of "mastered" and for the "debt", the share of the path from the base to perfection, because for a new rule of "mastered" the oracle is not a ceiling. A decisive run is 4,000 children a cell (R163 standalone);
    - **the guard** (guard) is a CI gate on every pull request. It runs the rule in force on the first 300 children of the generators G0–G3 and holds each number within two half-widths of the 95 % interval recorded beside it. The bands are recorded anew when a change moves the model on purpose, and the new file of bands is read in review;
  - the tolerance of the check "no worse" in standalone is the larger of the author's tolerance and the simulator's resolution, 4.3 standard errors: a tolerance finer than the resolution would fail an equal candidate by chance (R163 standalone);
  - the criteria of standalone chose the rating step, the rule of "mastered" and how much a wrong answer costs the child on the screen — the "debt". For all the rules the task was chosen by one and the same code of the service, so they did not judge the rule of choice (sources 1.1). In NovaTrail these are two repositories, and `engine` needs a criterion of its own;
  - the starting model of NovaTrail is the model of standalone; the differences are the level per module, forgetting, guessing by answer slots and the weights of evidence (concepts 11 spec; architecture 3.8 spec). What the first candidate is compared with and whether the simulator has an "oracle" of its own was not decided before T02; R04 decided it: the base is the first released version, the model's ceiling is the oracle (section 3.6);
  - the simulator and the criterion appear before the first candidate (repositories 6 spec).
- **Decided:** R04, 2026-11-07, by the author's answers in the planning of T02 and the proposals of the execution, before the first run of a candidate. The measures and invariants are section 3.5, the criteria of the model and of the engine on a common basis 3.6, the gate and the two-sided bands 3.7, the sizes of runs and the seeds 3.8.
- **Deferred:** the values of the base and of the ceiling that make up the path of the targets — the first decisive run of the base, before the first candidate (Д4 in table 4, [DEBT.md](../DEBT.md)); read and pinned in T26 — the 2026-11-09 amendment to R04, R28. Where the bands lie, the runner and the time of the gate, the order of releases and what the gate in the CI of `modules` consists of — T03 (section 2.3), decided by R05 (section 3.9).
- **Task:** T02, done.

### 2.3. How the CI of the libraries takes the simulator (Т-16)

- **Gist:** how the CI of `learner-model`, `engine` and `modules` gets `sim`, puts its own code in place and reads the gate; how long the gate takes; in what order the releases come out when a change breaks the API of a library that `sim` is built on, or moves the numbers on purpose and the bands have to be recorded anew in another repository. Of this, the card names among what is to be decided only the gate in the CI of `modules`, and Т-16 as a whole among what `sim` does (architecture 3.9 spec). Decided together with `spec`: Т-16 is a question of its register.
- **What is known:**

### 3.1. The virtual learner

**Words.** A virtual learner is a synthetic learner of the simulator: it has a truth of its own, which the simulator knows and the learner model estimates by its attempts. A population is a set of virtual learners that changes one assumption of the base population; in standalone it is a "generator" (sources 1.2). Until v0.9.5 the card called the populations profiles of virtual learners, but in `spec`'s vocabulary a profile is a learner in an account (concepts 15 spec; R26 spec), and a generator is the algorithm that gives numbers from a seed (R27, R59 spec). So here a profile is only in the vocabulary's sense, and the word "generator" is not said of populations; since v0.9.5 the card says "populations", and the vocabulary knows "virtual learner" and "population" (architecture 3.9, concepts 15 spec; R103 spec). On the simulator each virtual learner, like a profile of the platform, has modules, attempts and lesson runs.

**The learner's truth** is the simulator's own model, not the code of `learner-model`: the simulator measures the model on a learner it knows, not on a copy of the model. The base population holds the model's assumptions (R03, R04, R06 learner-model), as G0 in standalone holds the assumptions of standalone's model, and each population of section 3.2 changes one of them. In a module of the learner:
- **the grade and the starting band.** In olympiad maths the grade is from 1 to 6, evenly, in grade 3 maths it is 3, and the essays have no grade. The age category is one per learner, as for a profile, not per module: for a learner with a grade it is `under_13`, for `S-adult` `adult`, for a learner of essays one of the module's `audience.age_categories`, evenly. By it the simulator, as `api` does, selects the pool and the lessons (R107 spec; [format text](../spec/format/README.md), sections 14 and 21). The starting band and its shift 2.5 · (p − 1) are as in the model: the band whose grades name the learner's grade, and without a grade the first (R03 learner-model);
- **the module level** θ* is the shift of the starting band plus N(0, 1); each skill with the assessability `verdict` has an offset δ* from N(0, 0.5²). This is the base population of standalone, with skills instead of topics (sources 1.2). A learner of two modules has two levels, and the population sets the link between them (section 3.2);
- **a task's hardness** β* = 2.5 · (p − 1) + (d − 3) + miss, where p is the place of the task's band, d its difficulty, and the miss is how far the author erred in the difficulty: 0.5 · z, where z from N(0, 1) is one per task per run. The miss is a property of the task: all the learners of a population see it, and the populations of the miss change only the factor at the same z (section 3.3);
- **the answer of an item.** The item's first verdict is "correct" with the probability P* = c* + (1 − c*) · R̄* · σ(a · (θ* + δ̄* − β*)), otherwise "not yet". c* is the product over the item's answer slots: 1/k for a choice of k options and 0 for the others — for a number, a fraction and a time of day, `time`, as in the model (R41); δ̄* and R̄* are the means over the item's primary skills; the slope a = 1. The items of one attempt are independent given the truth. This is how the model computes P (R03, R04 learner-model);
- **the retention** R* of a skill is by the model's law, a power law: R* = (1 + F · Δt / τ*)^(−C), C = 0.5, F = 19/81, with the stability τ*, which starts at one day, τ₀. As in the model, a skill's τ* changes at most once per attempt, by the share of correct first verdicts S̄ of the skill in it: τ* := max(τ₀; τ* · (1 + g · (1 − R*))^S̄ · (1/2)^(1 − S̄)), g = 15 — after only correct ones it grows, after only "not yet" it is halved, but not below a day (R04, R06 learner-model). The truth's stability is moved by the learner's own answers, not by the model's estimate. The module level is not forgotten;
- **learning.** The base population does not learn, like G0; the main population is `G2-half` (section 3.2);
- **the attempt.** The learner answers all the items. After a wrong answer it answers again, on each of the three rungs of the hint ladder, and each rung adds 0.5 to the logit of the items that are not yet correct. From the fourth wrong answer the solution is shown: to a child by an adult action, as by default, and to a learner of the category `adult` by its button (concepts 10 spec; R82 spec). The close reason of the attempt is "correct" or "solution shown". The repeated answers do not count among the 200 answers of a run: the model reads the item's first verdict (R06 learner-model). It does not ask for a hint by the button, does not take a technique on request, does not abandon the attempt, and it has no "unreadable";
- **a lesson** it goes through segment by segment to the end, and the explanation and the example do not change the truth; a task of the lesson it solves like any other;
- **a task with a rubric** — in the essays — it writes, submits once and presses "Done": the close reason is "done" (concepts 15 spec). It has no verdict and no evidence (architecture 3.8 spec).

**The calendar.** The libraries get the time from outside (architecture 3.8 spec), and on the simulator `sim` gives it: days, sessions and breaks, not standalone's "every tenth answer is a new day" (sources 1.2).
- All the learners start on the same day. A day is a session with the probability 5/7, and a session is ten attempts in a row from 15:00 UTC: an item of a sheet takes two minutes, as in standalone, an item line of a workbook a minute, an essay fifteen minutes. The next task is issued at once. The time is whole seconds of UTC, as in the evidence (R08 learner-model).
- Day 0 of the calendar is 2026-09-07, a segment of a lesson without a task takes two minutes and comes before the lesson's tasks, the answers after a rung of the ladder take no time of their own, a skill's R* before the first attempt is 1, and a skill's last practice is the start of the attempt: these are the simulator's assumptions (R15). A learner has one grade, as a profile does — from the grades that each of its modules with grades names — and one age category — from the categories that each of its modules names.
- A learner's run in maths is 200 answers of items with a verdict, like the 200 answers in standalone; for the populations of forgetting, 180 days of the calendar, so that after the longest break at least 60 days remain; for the essays, until the module's tasks with a rubric that suit the learner's age category run out, but no longer than 60 days.

### 3.2. Populations

Each population changes one assumption of the base population of section 3.1; the two sides of one assumption get half of the learners each, by the parity of the learner's number. In code the populations are the package `internal/population`, and the assumptions are the fields of `learner.Assumptions` (R18). A population sets the learner, not the rule: what the engine gives `engine` decides, and the populations are the same whatever rule of repetition, of lessons and of the anchor skill at "does not know" it chooses (architecture 3.8 spec). Which measures are read on which population, and which of them are targets, is sections 3.5 and 3.6.

**The main population is `G2-half`**, as in standalone (R03): a learner that grows by one logit in 200 answers. The speed is the simulator's assumption, not a measurement: "How fast real children learn is not known: the speeds are the bench's, not a measurement" (sources 1.1). `G2` stays a stress test. The main population is for both maths; the essays have no verdict, and there is no main population there.

### 3.3. Graphs and tasks

- **Published packages.** The criterion and the gate run on the published packages of the three modules of the first slice, pinned by version: the simulator names the release of `modules` by the tag and the digest of the index (section 3.9), and each package by the module ID, the version and the digest, and reads its server part by the types `formatv0.CanonicalView` (R62, R72 spec; section 1). The release is embedded in `sim` itself — the package `internal/published` —, and the package `internal/pack` reads and translates it (R14). A file of a release of `modules` enters the code or CI of `sim` only after `release-verify` (RULES.md, Hard rules; R77 spec). A new version of a package on the simulator is a new pin, that is, a change of `sim`. Pinned now is the release `modules` v0.2.5: `olympiad-math` and `grade-3-math` 0.3.0 — their archives lie in the folder `v0.2.1/`, of the release that their entries name — and `english-essays` 0.2.0 from `v0.2.0/`, all in format 0.4: while the format is v0, the platform reads only its current version (the format text, section 2). Olympiad maths has 30 checks `time` and a leading question in 322 tasks, school maths a worked example in every lesson (R42). Before that, `modules` v0.2.0, all three modules at version 0.2.0 (R32), and earlier still `modules` v0.1.4 with `olympiad-math` 0.1.1 (R31).
- **Synthetic packages.** `sim` also has synthetic packages of its own, in the form of the three modules — a sheet with choices, numbers, `predicate` and the time `time`, with leading questions and three bands of grades 1–6; a workbook of one band of grade 3 with pages of up to ten items and a skill that teaches an anchor skill; and essays with a rubric, without grades —, and a graph where a skill of another module rests on an anchor skill. This is a canonical view that the simulator assembles, not the content of `modules`: for the code and the tests of the simulator, not for judging candidates. There are no learners' data in them (RULES.md, Hard rules). In code it is the package `internal/synthetic`, with the module IDs `synthetic/…`, which the criterion and the gate reject, and the anchor skill of the shared taxonomy `core.multiplication-table`, which the workbook teaches and on which the sheet's skill rests; the views pass the format's schema of the canonical view (R19).
- **The graph** for both libraries is built by the simulator with a function of `learner-model`, from the skills and the task descriptions of the module, in the types of `learner-model` (R28 spec; architecture 3.8 spec; section 1).
- **The task.** The band and the difficulty give the model's β and the truth's β* (section 3.1); the check kind and the number of options of each answer slot give the truth's c* and the model's c; the simulator reads the leading question only as the fact that the task has one — the request of `G8` gives it (section 3.1; R41). The simulator chooses a template's instance by the attempt's seed with the same choice as the platform: the place with the names `template`, the task ID and `instance` ([format text](../spec/format/README.md), sections 22 and 23; R60 spec). For the engine a template is one task, and a template has one miss for all its instances.
- **The miss.** In standalone a chat model wrote the task, and the miss was drawn at every issue (sources 1.2). In NovaTrail the author writes the task, and the author's error in difficulty is one per task: the simulator draws z once per task and run, and the miss is a multiplier of z — 0.5 in the base population, 0, 0.25 and 1 in `G0-exact`, `G0-miss0.25` and `G0-miss1`. So all the learners of a population see the same task, and the populations of the miss see the same error of the author to another degree, as in standalone, where a population's spread is a multiplier of the same numbers. `G4-band` adds a shift of the band to the miss. No fields of the format are needed for this: the miss remains an assumption of the simulator, as does its spread.

### 3.4. Seeds

- **Places of randomness.** Every number of the simulator comes from a place of randomness of the format: the run's seed and names ([format text](../spec/format/README.md), section 22; R27, R59 spec). The names are the experiment, the unit and the purpose, so `seeded` of standalone's simulator is a particular case (architecture 3.9 spec). The unit of a virtual learner is `<population>/<number>`, the unit of a task `task/<module ID>/<task ID>`, with the purpose `miss` for its z (section 3.3). The learner's purposes:
  - `params` — the learner's truth: the grade, the level, the offsets, what the learner's population differs by, the band of `G4-band`;
  - `calendar` — the days, the sessions and the breaks, and which day is bad in `W-badday`;
  - `answers` — the first answers of items: the learner's k-th first answer takes the same numbers in the same order whatever happens, as in standalone, so the learner meets the same numbers under any rule;
  - `retries` — the answers after the rungs of the ladder and the answer the learner writes again after "unreadable": a stream of its own, so that the repeats under one rule do not shift the first answers;
  - `attempts` — the learner's k-th attempt takes the same numbers in the same order: the shift of `W-shock`, the error of `W-error`, the technique of `G8`, the segment where `L-abandon` abandons the lesson, and the leaving of `E-leave`;
  - `attempt` — the seed of each attempt, for the instances of templates;
  - `choice` — the seed of the engine choice, if the rule of `engine` needs randomness (R59 spec). The first version of the rule takes no randomness, and the seed of the choice is empty (R07 engine; R107 spec): the purpose stays reserved by the simulator in case a new version takes randomness.
- **Populations do not shift one another.** A new population is new names of units, and the numbers of the learners of other populations stay as they were, as in standalone (sources 1.2).
- **Working and held-out learners.** The held-out learners take a seed of their own and a name of the experiment of their own: the format says to take a seed of one's own when streams must stand apart from others' ("a use that needs streams apart from another's takes a seed of its own", [format text](../spec/format/README.md), section 22). A test of the code shows that no learner is drawn alike in two sets, as in standalone, and on the held-out learners a choice is confirmed once (R163 standalone). The seeds themselves are section 3.8.
- **The normal and the exponential distributions** are the simulator's own: the format does not give them, and the simulator builds them on `fraction` ([format text](../spec/format/README.md), section 22; architecture 3.9 spec). What is required of them is the same bits on any build of one version, as in `learner-model` (R09 learner-model): otherwise the gate's bands would part in the last digits on another processor (section 2.3). Decided by R12: the normal one is the inverse distribution function by AS 241 on one `fraction`, with `detmath.Log` and `math.Sqrt`, the exponential one is `0 − ln(1 − u)` with `detmath.Log`, and every product goes through `float64()`; the golden bits are held by a test on all the builds of `same-bits`. The place of randomness is the package `internal/seed`; the gate's runner is section 3.9.

### 3.5. Measures

A measure is read from the learner's truth of section 3.1, which the simulator knows, and from what `learner-model` and `engine` gave. The simulator has three layers of checks: the invariants, which hold on every learner; the measures, of which the criteria are made up (section 3.6); the gate's numbers with bands (section 3.7). The names of the measures are for the simulator's reports and for the bands, as the names of `cells.csv` in standalone (sources 1.2).

**True mastery.** A skill is mastered by the truth at a band when the P* of the reference task — of difficulty 3 at that band, without a miss, with a choice of five options and at R* = 1 — is at least 0.775, the middle of the corridor. This is standalone's "truly mastered" (sources 1.2): the same answer at a guessing of 0.2. The reference does not depend on the model's threshold, 0.71875 (architecture 3.2 learner-model), though at this guessing it coincides with it: the truth does not read the model's numbers (R03). The truth "knows" an anchor skill when at least one skill that teaches it is mastered by the truth, with R* at the time of reading — so with the truth knowing fades, and with the model it does not (R07 learner-model). The population `A-fading` reads true mastery the same way (section 3.2).

**Invariants** have a tolerance of zero: one violation on one learner is a red run, and a red gate too. The package `internal/invariant` holds them (R17); `I2` checks the meaning of a code by the facts that it names, and the order of "longest" and reachability belong to the rule of `engine` (the 2026-11-08 amendment to R04).

| Name | What holds |
|---|---|
| `I1` reproducibility | A run repeated on the same seeds gives the same bits of every choice, of every piece of evidence, of the model's state at the end and of every number of the measures — the state after each step follows from the evidence, and the same bits of the evidence and of the final state hold it too (R17); a choice repeated from the input that it stores is the same choice (concepts 12 spec; architecture 3.8 spec) |

| `E3` repetitions | The true R* of a skill when the engine gives it as a repetition, on average; the share of repetitions where the P* of the reference task of the mastery band is already below 0.775 — the lateness; the share of repetitions among the choices by weeks of the calendar (a proposal of `learner-model`, architecture 3.2 learner-model); the mean R* of the skills mastered by the truth on the last day of the run | `F-` |
| `E4` coverage | The share of the reachable skills that were issued at least once, and the share of the skills mastered by the truth by the end of the run. The truth grows from the choice only through which skills the learner answers, through the stability τ* and through the lessons of `L-explain` (section 3.2), so coverage is what the choice moves the truth by | `G2-half`, `G2`, `L-explain` |
| `E5` essays | How many tasks with a rubric the learner wrote by the end of the run, and how many times the learner was given a task that they had already closed | `E-base`, `E-leave` |

In code the measures of the engine are the same package `internal/measure`. What the truth says about the pool at a choice — the ceiling of `E1`, whether there is anything to give, the reachable skills — the run records before the engine choice, `run.Pool`. A skill's reachability is by the truth: the truth holds its prerequisites, and the pool has a task on it that the rule could give. The P* of an issue is the truth's chance without what only the attempt holds (R23).

The engine's criterion reads the false "mastered" of `M4` and the lag of `M3` too: which tasks the engine gives moves the estimate as well (section 3.6).

### 3.6. Criteria

Two criteria — of the learner model and of the engine — on a common basis (R04). They are written down before the first run of a candidate, so that a candidate's numbers do not influence what it is judged by (R163 standalone; architecture 3.8 spec).

**The common basis.**
- **A cell** is a rule, a population and a graph. The rules of a run are the base, the candidates and the ceiling. **The base** is the first released version of each library (R12 learner-model; R103 spec), and after the first choice, what was chosen. Of the first two judgements — of the model and of the engine — the one whose candidates are ready first goes first, and the second runs the base anew, with what the first chose; the path stays pinned (R35). The first judgements — of the engine, then of the model — both ended in an exit, so the base stayed as it was, and the second judgement ran on it (R36, R37). The second judgement of the model, `model-2`, chose `theta` — `learner-model` at commit a063835, the level of a module forgets after a pause — and the held-out learners confirmed it, so the base is now that commit, and the judgement `engine-2` goes on it (R46). **The model's ceiling** is the oracle: its estimate is the truth θ* + δ*, its P is P*, and it sets "mastered" by true mastery; it is the ceiling of every model that learns of a learner from answers, and for the rule of "mastered" the ceiling is perfection: not one false one, and without waiting, as in standalone (sources 1.1). **The engine's ceiling** is a choice with the same model but by P* from the same pool: the task with the largest share of items whose P* is in the corridor, and on a tie, the one whose mean P* of the items is closer to 0.775, since the engine chooses a task as a whole, not an item (R104 spec). The ceiling's pool has the same exclusions as the rule's: a task with a seen solution — not as the next task, and after the pause of `engine`, with the second pass (R82 spec; R03 engine), or the ceiling would take tasks that the rule has no right to give; a repetition — when the P* of the reference task falls to 0.775.
- **In code** (R24): the oracle is read on the answers of the same run as the model — `measure.Oracle`; the recipe `just decisive` runs a candidate's decisive run with `CANDIDATE_LEARNER_MODEL` or `CANDIDATE_ENGINE`, and a pair's with both and `CANDIDATE_PAIR=yes` — by a commit by its full SHA or by a folder without uncommitted changes —, and the simulator is built through the gate's workspace, and the base by `go.mod` (R34); the engine's ceiling is the run's rule `run.Ceiling` on the pool `run.Pool`, and where the pool gives no task with P* — tasks with a rubric, lessons, "nothing to give" — `engine` chooses; each build writes a results file of `sim run` — JSON Lines, a line per learner, with the version or the commit of each library —, and `sim compare` reads two files in pairs by learner, `measure.ReadPair`.
- **The judgement** (R25; the 2026-11-09 amendment to R25): the criteria are the package `internal/criterion` and the command `sim judge` with a judgement file that names the runs of the base, of the candidates and of the confirmation. The judgement file, the report of `sim judge` and the SHA-256 of the runs lie in the repository, in `judgements/<criterion>-<n>/`, and a decision of the log records the result (R35). The judgement takes the path of each measure from the pinned file of paths, not from the judgement's runs, so it needs no run of the ceiling. A check stands where the base reads the number; the path of `E1` in the model's criterion goes to the engine's ceiling; the report names a decisive run or a rough look, and the graphs of the choice. The judgement refuses whole a run that is not of this judgement (R40): the base and the base of the confirmation run on the libraries on which the paths were read and the gate pinned — `sim` embeds `gate.json`, as it does `paths.json` —, and a candidate of one library, and the same candidate on the held-out learners, run on the base's second library: at its version or at the commit of its pin, as the recipe of the decisive run builds it (R34). A pair has no second library.
- **The numbers** are over all the learners of a cell, with a 95 % interval from 2,000 resamples of the learners. A comparison is the difference of two cells on the same learners, with an interval from the same resamples in both. Cells of the same learners are runs with the same seeds (section 3.8), and a pair is compared learner by learner: two versions of one library do not go into one Go build, and the code epic decides how to run them side by side; the gate takes each by a commit from the gate file (section 3.9).
- **A decisive run** is 2,000 learners a cell, on the working learners; until T36 it was 4,000, until T41 1,000, until T46 1,500 (R33 and the 2026-11-11 and 2026-11-12 amendments to it). A smaller run is a rough look: its report is named so, and it decides nothing.
- **"No worse":** the worse end of the 95 % interval of the paired difference with the base is within the tolerance. The tolerance is the larger of the author's tolerance and the simulator's resolution: 4.3 standard errors of the paired difference of the candidate and the base on this check, in the same run (R04). So a candidate equal to the base passes the check 99 times in 100, and dozens of checks do not fail it by chance (R163 standalone). The standard error is the noise of the comparison on these learners, not the level of the candidate's numbers; standalone read it on a pair of rules already on its simulator, and `sim` has no such close pair (R04). The author's tolerances are a proposal made in execution: 0.01 logit for `M1`, `M3` and `M7`; 0.002 for Brier and 0.01 for the bias of `M2`; 1 percentage point for `E1`, the shares of `E2`, `E4` and `M3`; 2 points for `M4`, `M6` and `M9`; one answer for the counts of answers of `M3`, `M5` and `M6`; 0.01 for R* and 2 points for the lateness of `E3`; one task for `E5`.
- **Direction.** In the criterion every measure goes so that less is better: a signed measure by its absolute value, as `|r6_lag|` in standalone (sources 1.2) — the bias of `M1` and `M2`, `M3` —, the error of `M7` by the root mean square; a share where more is better by its shortfall from one: the share in the corridor of `E1`, the R* of `E3`, the shares of `E4`. So the check "no worse" and the path read the same way for all the measures.
- **Targets** are a share of the path from the base to the ceiling. The path is the base's value minus the ceiling's value, both in this direction; the share that a candidate closed is the base's value minus its value, divided by the path. The base gets 0, the ceiling 1. The values of the base and of the ceiling that make up the path are read on the decisive run of the base before the first candidate, and anew when what they were read on changes: the graph and the tasks of the pinned packages, the base or the size of the decisive run, as in T30, T36, T41, T43, T45, T46 and T47 — in T45 only the version of the base's library changed, and the numbers are the same, but the judgement holds the base to the libraries of the paths (R40); a pin of packages on the same libraries that does not shift the base's numbers leaves the paths, as in T37 —, and they are pinned by an amendment to R04: this is calibration, not a choice, as c* in standalone (sources 1.2). A path no greater than zero — the ceiling no better than the base — leaves the share of that measure unread: the measure leaves the score together with its weight, the report names it, and the target on it is not met. A measure whose path is positive but no greater than the author's tolerance of that measure leaves the same way: a ceiling no farther from the base than the tolerance sets no path, and for a measure with a path to perfection, neither does a base no farther than the tolerance from it; the report names such a measure separately (the 2026-11-09 amendment to R04). For the measures where the ceiling need not be better, the path goes to perfection: not one false one, no waiting, no lateness, all the skills mastered. **In code** (R28): the paths are pinned by the file `internal/criterion/paths.json`, embedded in the simulator. `sim paths` writes it from the decisive runs of the base and of the engine's ceiling: the base's value, the ceiling's value in the criterion's direction and the path of each measure of the score groups on each cell of a published graph. The values are measurements 3.1, by the 2026-11-13 amendment to R04, "the base on `theta`": on `learner-model` at commit a063835, `engine` v0.1.6, the packages of `modules` v0.2.5 and 2,000 learners. Until T47 the table of the values stood in the amendment to R04 itself (the 2026-11-13 amendment to R28). The judgement takes the path from this file at every choice and in every confirmation: a candidate's share is its paired difference with the judgement's base divided by the pinned path.
- **A number that the run did not read** leaves the constraint unmet and the score unread. The exception is a graph whose package is not published yet: its checks stand in the report as "no graph", neither met nor failed, and the choice names the graphs on which it was made. A new published package is a new pin in `sim` and new bands of the gate, and earlier choices are not revisited by themselves (R04).
- **Better:** a candidate is better than the base when the interval of its score is above zero, and better than another candidate when the interval of the paired difference of their scores is above zero. The score is the weighted sum of the paired differences with the base at the pinned path; its interval is from resamples of the learners of each population separately.
- **The choice:** among the candidates that hold all the constraints and are better than the base, A* is the one with the largest score, and its equals are those whose difference with A* holds zero in its interval. The simplest of them is chosen: with the smallest number of changed constants, then without a new field in the model's state or in the engine's input, then the closest to the base.
- **The confirmation:** the chosen candidate is run once more, one time, on the held-out learners of this choice, by a decisive run, beside the base; the path is the pinned one (R28). There too it holds all the constraints and is better than the base. If not, it is the exit: no second candidate is tried on the same held-out learners, because a set that has been looked at is no longer held out (R163 standalone).
- **The exit:** if no candidate passed or the chosen one was not confirmed, the base stays as it is.

**The model's criterion.** It judges a change of `learner-model`: the step and the uncertainty, "mastered", the scale of bands and the start, guessing, forgetting, the weights of evidence, the anchor skill. The first candidates are the numbers that waited for the simulator (Д5–Д7 in table 4 of RUN.md of `learner-model`): the judgement `model-1` ended in an exit (R37). The second round is epic E5 of RUN.md of `learner-model`.
1. **Constraints** — each holds:
   - the invariants `I1`–`I4`;
   - the floor of the first slice — "mastered" is not declared too early (product 10 spec): false "mastered" of `M4` at most 20 % on `G0` and `G0-skills1`, and the number of answers before "mastered" of `M6` at most 1.5 times the base's, on the same populations, as in standalone's choice of "mastered" (sources 1.2);
   - "no worse" than the base — on every population with a verdict: `M1` after 200 answers, `M2` Brier, `M4`, `M6` — the share not declared, `E1` — the share in the corridor; on their own populations — `M3`, `M5`, `M7`, `M8`, `M9`, `M10`, `E3`;
   - the targets — for a candidate that names them as its target, as the step in standalone: on `G2-half` the lag of `M3` closes at least 0.55 of the path to the oracle, and the corridor of `E1` at least 0.27; on `G3` the share not caught up after the jump is at most 25 %. These are standalone's targets written as a share of the path: the lag at most 45 % of the service's, and c* = 0.27 (sources 1.2). A candidate with another target holds the floor and "no worse", and its target is its score group below.
2. **The score** is the share of the path from the base to the oracle, averaged over the measures of a population, weighted by populations and groups. A candidate names its group, and the interval of that group's score is above zero too: an improvement where the candidate promised it.

| Group | Weight | Populations | Measures |
|---|---|---|---|
| Stays put | 1 | `G0` | `M1` after 200 answers; the shortfall of `E1` |
| Learns | 2 | `G2-half` 1.25, `G2-fading` 0.5, `G2` 0.25 | the absolute value of `M3`; the shortfall of `E1` |
| Changes at once | 1 | `G3` 0.4, `G3-drop` 0.4, `F-break` 0.2 | the number of answers until catching up of `M3` |
| Out of its band | 0.5 | `G1` 0.375, `S-adult` 0.125 | `M7` after 10 answers; the share of hard first items of `M7` |
| "Mastered" | 1 | `G0` 0.5, `G0-skills1` 0.5 | `M4`; `M6` — the number of answers before "mastered"; the path — to perfection |
| Forgets | 1 | `F-model` 0.4, `F-exp` 0.2, `F-C1` 0.2, `F-growth5` 0.2 | Brier of `M2` after pauses from 7 days; `M5`; `M4` after a break |
| Pages | 1 | `W-shock` 0.5, `W-error` 0.25, `W-badday` 0.25 | Brier of `M2` by the items of pages; `M4` from one or two pages |
| Anchor | 0.5 | `A-fading` 0.25, `A-unpractised` 0.25 | `M9`; the path — to perfection |

A population's weight is a share of the group's weight: the weights of a group's populations sum to its weight, as in "Learns" in standalone, 2 = 1.25 + 0.5 + 0.25 (sources 1.2). The first four groups and their weights are as in standalone's choice of the step; in "Changes at once" and "Out of its band" `F-break` and `S-adult` are added to its populations, and the shares of `G3`, `G3-drop` and `G1` are reduced for them. The new groups and their weights are a proposal made in execution (R04).

**The engine's criterion.** It judges a change of `engine`: the corridor, prerequisites, consolidation, the queue, probes, repetition, lessons, the anchor skill under "does not know".
1. **Constraints:**
   - the invariants `I1`–`I4`;
   - being stuck, `E2`, no more than the base's, with the tolerance;
   - "no worse" than the base — `E1` on every population with a verdict, `M4` and `M3` where the model's criterion reads them, `E3` on `F-`, `E4`, `E5` on `E-`, `M9` on `A-`;
   - the target — the score group that the candidate names as its own: the interval of its score is above zero. The engine has no number for the target: standalone's c* = 0.27 is a share of the path to the model's oracle in the choice of the service, and the engine's path goes to another ceiling, and carrying the number over would mean making up a number.
2. **The score** is the share of the path from the base to the engine's ceiling, and where there is no ceiling, to perfection:

| Group | Weight | Populations | Measures |
|---|---|---|---|
| Corridor | 2 | `G2-half` 1.25, `G0` 0.5, `G2` 0.25 | the shortfall of `E1` |
| Repetitions | 1 | `F-model` 0.5, `F-exp` 0.25, `F-growth5` 0.25 | the lateness of `E3`; the shortfall of R* on the last day of `E3`; the path — to perfection |
| Coverage | 1 | `G2-half` 0.75, `L-explain` 0.25 | the shortfall of the share of skills mastered by the truth by the end, `E4`; the path — to perfection |

The populations' weights are shares of the group's weight, as for the model. The engine's ceiling gives the path only for the corridor: a choice by P* holds the corridor, but need not cover more skills or repeat on time. The weights are a proposal made in execution (R04).

**A candidate pair.** A change of two libraries at once — a new constant of the threshold "mastered" of `learner-model` together with a new target of the corridor of `engine` (the 2026-11-02 amendment to R23 spec) — is run as one pair against the pair of bases on the same learners. The pair holds the constraints of both criteria and is better than the base by the score of the library whose target it names, and the interval of the other's score does not lie wholly below zero. How the gate runs a pair when a pull request substitutes one library is section 3.9: the gate file names both commits.

### 3.7. The gate and the bands

The gate is standalone's guard (sources 1.1): it does not choose the rule but holds what the rule was chosen for. It runs on every change of `learner-model`, `engine` and `sim` itself — on the commits of the libraries that the gate file names, with the change's code substituted (section 3.9). In the CI of `modules` the gate holds invariants and thresholds, not bands: an edit of content moves the numbers by design (section 3.9; the 2026-11-07 amendment to R04).
- **Learners:** the first 250 working learners of the gate's populations (300 until T30, 100 until T41, 150 until T46; R31), on each published graph where the population runs: `G0`, `G1`, `G2`, `G2-half` and `G3` on both maths; `F-model` on both; `W-shock` on school maths; `A-linked` on both together; `E-base` on the essays. The run of each learner is as in a decisive one, by section 3.1: 200 answers in maths, 180 days in `F-model`, until the end of the tasks with a rubric in the essays.
- **Invariants** `I1`–`I4` — on every learner of the gate; `I1` by a repeat of the run. The gate takes the choice anew at every step only for the first 10 learners of a cell: the repeat holds `I1` to the bit, and choosing anew for all would double the engine's work; the first 10 catch a rule that changes its input in place the same way in both runs (R31). In the same way — only for the first 10 — the decisive run, which has no repeat, takes the choice anew too (R33).
- **The gate's numbers:**
  - `G0` — `M1` after 200 answers, the share in the corridor of `E1` and the share of items with P* below 0.50, `M4`, the number of answers before "mastered" and the share not declared of `M6`;
  - `G1` — `M7` after 10 answers;
  - `G2` and `G2-half` — `M3`, the share in the corridor of `E1` and the share of items with P* below 0.50;
  - `G3` — the share not caught up after the jump of `M3`;
  - `F-model` — Brier of `M2` after pauses from 7 days, `M5`, the lateness of `E3`;
  - `W-shock` — `M4` from one or two pages;
  - `A-linked` — `M9`, on both maths together (section 3.2; R31);
  - `E-base` — `E5`;
  - on all — the share of learners stuck of `E2` and the share of "nothing to give" with a non-empty pool.
- **A band** is the recorded value of a number and half the width of its 95 % interval, from the same resamples. A number is in its band when it is no more than two half-widths from the recorded one, the edges included. The gate's learners are always the same, so code that shifted nothing reads the recorded numbers to the last digit: a band is room for a change, not for chance (sources 1.2). A number that the run did not read is outside the band.
- **Two-sided.** A number beyond its band is a red gate, for better or for worse: the gate prints a table of all the numbers against the bands and names each number outside its band with the band itself (R04).
- **In code** (R26): the gate's cells and numbers are the package `internal/gate`, the bands are in `gate.json`. The half-width is half the 95 % interval from the same 2,000 resamples. A number that the recording did not read is recorded as "not read", and the gate holds exactly that. The gate runs `A-linked` on the pair of published maths (R31); before the pin of T30 it ran only on synthetic packages, and the report called its numbers "no graph". `sim`'s own CI holds the numbers as recorded to the bit (`just gate exact`), the callers to the bands (`just gate`). `just gate record "<reason>"` records the bands. The first file of bands was recorded in T26 on the commits of `learner-model` v0.1.0 and `engine` v0.1.0, the releases of the base (R28). The second in T30, on the new pin and on 100 learners (R31). The third in T41, on `engine` v0.1.6 and 150 learners (the 2026-11-11 amendment to R31). In T42 the bands were recorded anew only for the sake of the reason, on `learner-model` v0.1.5 — the values the same to the bit (R41) —, and in T43 on `modules` v0.2.5: 39 numbers of 69 the same to the bit, `E1.hard` of `G0` of olympiad maths 0.320 → 0.374, and `E2.stuck` of `G0`, `G1` and `G2` of olympiad maths became non-zero (the 2026-11-11 amendment to R26; R42); in T45 again only for the sake of the reason, on `learner-model` v0.1.6 — the values the same to the bit (the 2026-11-11 amendment to R26; R43); in T46 on 250 learners: the half-width is on average 0.79 of the former one, and three numbers of school maths, unread before, are read (the 2026-11-12 amendment to R26 and to R31); in T47 on `theta`, the chosen candidate: 8 numbers of 69 moved, all of `F-model`, each by less than one former half-width (the 2026-11-13 amendment to R26; R46). The gate has held the share of items with P* below 0.50 and the share of "nothing to give" since T25: the thresholds of the CI of `modules` are taken from them (R27, section 3.9).
- **Recording anew.** A pull request to `sim` records the bands anew, with a reason: for a chosen candidate, its report of the criterion, the decisive run and the confirmation; for a change that is not a candidate — a new pin of a package, a move, an edit of the simulator — the gate's table before and after. The new file of bands is read in review, as a snapshot is: recording turns a red gate green, and only the review sees why (sources 1.2). The bands lie in the gate file in `sim`; the runner, the gate's time, the order of releases of `sim` and of the libraries, and the gate in the CI of `modules` are section 3.9.

### 3.8. Sizes of runs and seeds

- **Sizes:** a decisive run and a confirmation are 2,000 learners a cell (4,000 until T36, 1,000 until T41, 1,500 until T46; R33 and the 2026-11-11 and 2026-11-12 amendments to it); a rough look is fewer than 2,000 and decides nothing; the gate is the first 250 working learners of a population (300 until T30, 100 until T41, 150 until T46; R31). The recipe `just decisive engine|ceiling <file> [set]` runs a decisive run — the set `working` or `held-out-<criterion>-<n>`, and the candidate from `CANDIDATE_LEARNER_MODEL` and `CANDIDATE_ENGINE` (R34): processes by parts of the learners, on all the machine's cores, then `sim merge`; since T36 with the choice anew for the first 10 learners of a cell and with a process on one processor and `GOGC` 400 (R33). Its time at each pin, with the host's load, is measurements 1.3: the sizes above were chosen by it (R33 and the 2026-11-11 and 2026-11-12 amendments to it). The files of its results do not lie in the repository — their size is in measurements 1.3 too: the same seeds and the same bits on any build give them anew to the byte, and the file of paths names their SHA-256 (R28). Between judgements they lie in `runs/` of the working copy, which `git` does not see, and a judgement runs only the candidate (R33).
- **The working learners** — the seed 20261107, the experiment `working`. The gate and the decisive runs take the same working learners, as standalone's guard and runs do (sources 1.1).
- **The held-out learners** are each choice's own: the seed and the experiment `held-out-<criterion>-<n>`, where the criterion is `model`, `engine` or `pair`, and n is the number of the choice of that criterion. The model's first choice — the seed 20261108, the experiment `held-out-model-1`, looked at by the judgement `model-2` and no longer held out (R46); the engine's first choice — the seed 20261109, the experiment `held-out-engine-1`. The seed of each next choice and of each pair is written down by an amendment to R04 before the first run of its candidate: a set that has been looked at is no longer held out, and two choices do not share one set.
- **Places** — by section 3.4: the names are the experiment, the unit, the purpose. A test of the code shows that no learner of any population is drawn alike in two sets.
- **A seed as a number** is an unsigned 64-bit integer, written in decimal digits ([format text](../spec/format/README.md), section 22). 20261107–20261109 are dates from the day of writing, as 20261001 and 20261003 in standalone (sources 1.2).

### 3.9. The gate in CI

How the CI of `learner-model`, `engine` and `modules` takes the gate of section 3.7 (R05). The way is `go.work`, the recommendation of Т-16, and `spec` closed Т-16 with the answer of `sim` (R103 spec; R06): the runner, the gate's time and the changes it runs on live in the three repositories' own workflows (R03 .github; architecture 3.2 .github).

**The gate file** lies in `sim`, beside the simulator's code, and names everything its numbers were recorded on:
- the commits of `learner-model` and `engine`, by full SHAs. A commit of a released version, or a commit of a pull request not merged yet — the order of releases below;
- the packages — the tag of the release of `modules` and the digest of its index, as the configuration of `api` pins them (R63 spec), and each package by the module ID, the version and the digest (section 3.3). By the tag the job downloads the index and its signature, `release-verify` accepts the index, and the job takes the packages by the digests from the index, from the release that their entry names (R77 spec; architecture 3.10 spec);
- the versions of the shared dependencies that the workspace chose at the recording — of the Go module `spec`, and the `go` line of each module (below);
- the bands — the value and the half-width of each number of the gate (section 3.7).

The code epic chose the form of the file: `gate.json` at the root of `sim`, JSON (R26). The gate builds the simulator only on the commits from the file — at the callers and in its own CI too: the gate recipe of `sim`, which its gate job calls, writes `go.work` from the file into a temporary folder and points `GOWORK` at it, and does not take the versions from `go.mod`. This workspace is written by the hidden recipe `workspace`, one for the gate and for a candidate's decisive run, and `sim gate verify` holds the candidate's build before the run — the same check as the gate's, without bands (R34). The job "Go" of the shared `go.yml` runs the tests of the simulator's code without `go.work`, on the versions from `go.mod`: there is no gate in `ci-test` (R09). So that its jobs stay green when the file names a commit that is not in any release yet, the `go.mod` of `sim` names each library at the same point as the file: by the tag of the release, and while there is no release, by the pseudo-version of the commit. The Go proxy serves a commit by SHA, and the gate checks `go.mod` against the file (R26). Earlier this sentence spoke of a lower bound: then an edit of the simulator for an API that is not in a release would have brought down the job "Go" until the library's release. `go.work` makes each commit from the file a main module, and a main module has no version and is taken as it is, whatever version `go.mod` requires ("MVS starts at the main modules (special vertices in the graph that have no version)", sources 2.1). So the caller runs exactly what the numbers were recorded on, except its own code.

**How a caller takes `sim`.** By a CI job of its own, not by the shared `go.yml`: that one runs the caller's recipes on the caller's own code, and has nothing to fetch `sim` and the second library with and to build them through `go.work`. It had no inputs (architecture 3.1, 3.2 .github), and the only one that came with v0.1.18 of `.github`, `same-bits`, adds runs on other builds of the same code (architecture 3.11 spec; R08). The job:
1. fetches `sim` by the tag and the SHA of its commit, written in the caller's workflow: the tag for reading, the SHA as what holds the content, as with actions pinned by SHA (RULES.md, Hard rules). `sim` is taken as source from git, not as a release file, so it needs no `release-verify`; the packages of the modules, by the index from the gate file, which `release-verify` has accepted (above);
2. fetches the second library by the commit from the gate file of that tag;
3. writes `go.work` on the fly — `use` of the three modules — and does not commit it. The Go documentation advises CI not to take a `go.work` committed into a module — "CI systems should generally not be allowed to use the go.work file" (sources 2.1): the library runs its own tests without it, and the gate measures the library precisely inside the simulator;
4. builds and runs the gate in the stage `toolchain` of the devcontainer of `sim` at the same tag: Go and the tools are those on which the numbers were recorded, after the pattern of the job `go-arm64` of `learner-model`, which builds its own stage `toolchain` and runs a recipe in it (R09 learner-model).

If the caller's code breaks an API that `sim` or the second library is built on, the build fails and the gate is red. The Go documentation does not say this in words; it is an inference: `use` substitutes the code, and code that lacks an API does not compile.

**Shared dependencies.** The three modules of the workspace have one build, and for a module that several of them require MVS chooses one version — the highest required (sources 2.1). So a library in the gate may build with another version of the Go module `spec` than the tag of its submodule (R64 spec). Therefore the file names the chosen versions of the shared dependencies, and the gate checks the chosen ones against the recorded ones: another version is a red gate with a reason, as another commit is. Aligning them is a move of the caller or of `sim` to a tag of `spec` by a task of its own, with new bands if the numbers shifted. `learner-model` takes only Go's standard library (R09 learner-model), so for it this is only the `go` line. The gate does not change the compiler: a module's `go` line newer than the Go of the stage `toolchain` of `sim` is a red gate with a reason. The check `sim gate check` holds this: the `go` lines of the three modules equal those recorded in the file and are no newer than the Go the gate is built with (R26).

| CI | When it runs | What is taken | What is substituted | What it holds |
|---|---|---|---|---|
| `learner-model` | every pull request and every commit of `main` | `sim` — tag and SHA; `engine` — the commit from the file; the published packages from the file | the code of `learner-model` | the invariants and the gate's numbers within the bands (section 3.7) |
| `engine` | the same | `sim` — tag and SHA; `learner-model` — the commit from the file, whatever version the `go.mod` of `engine` requires; the packages from the file | the code of `engine` | the same |
| `modules` | a pull request where what the simulator reads from a package has changed, and a pull request that changes the tag of `sim`; none in a format transition, where `modules` changes nothing of what the simulator reads except the writing itself in the new version of the format (R03 modules; the 2026-11-07 amendment to R103 spec) | `sim` — tag and SHA; both libraries — by the commits from the file | the packages that the pull request built | the invariants and the thresholds below, without bands |
| `sim` | every pull request and every commit of `main` | both libraries — by the commits from the file; the packages from the file | the code of `sim` | the invariants and the gate's numbers within the bands |

The gate still runs a pull request of `engine` that raises the version of `learner-model` in its `go.mod` on the commit of `learner-model` from the file: a new pair of libraries is a change that passes through the simulator, and `sim` records it like any other.

**The gate in the CI of `modules`** judges not a library but content, and an edit of content moves the numbers by design. So it has no bands (the 2026-11-07 amendment to R04):
- **what changed.** Whether what the simulator reads has changed, `sim` itself decides: its command compares the canonical text of what the simulator would read from the server part of the pull request's package — the manifest, the graph and the tiers, the tasks, the lessons and the instances of templates, without the texts for the learner — with the same of the newest published version of the module of the same format version, as `modules` compares the graph (R03 modules). A new module has changed whole. So the list of what the simulator reads lives in one place — in the simulator's code;
- **learners** — the first 250 working learners of the gate's populations (section 3.7) on the graphs of the modules that changed. `A-linked` runs if at least one of the maths changed, on the packages of both from the pull request: the CI of `modules` builds all the modules (R03 modules), and `sim gate changed` also gives out an unchanged module that a graph of a gate population holds together with a changed one (R31);
- **what it holds** — the invariants `I1`–`I4` and the thresholds of the first slice, where the engine holds the corridor, does not get stuck and does not declare "mastered" too early (product 10 spec). The thresholds are a proposal made in execution (R05):
  - `E2` — the share of learners stuck and the share of "nothing to give" with a non-empty pool no more than on the published graphs, plus the author's tolerance, 1 percentage point (section 3.6): the largest value of `E2` in the gate file at the same tag of `sim`. Content must not add being stuck to what the engine already has, and the engine is judged by its criterion, where `E2` is "no more than the base's" (section 3.6). An absolute zero would hold every pull request of `modules` red if the accepted engine gets stuck for even one learner;
  - `E1` on `G0` and `G2-half` — the issued items with P* below 0.50 no more than their largest share in the gate file on these populations plus 1 point, and the share in the corridor no less than the smallest less 1 point (the 2026-11-09 amendment to R05). The former thresholds — 25 % and half the pool's ceiling — were not met on the published packages with the base engine in any cell: the gate would have been red on every pull request. They remain a target of the engine's criterion;
  - `M4` on `G0` — false "mastered" at most 20 %, as the floor of the model's criterion (section 3.6);
  - `E5` on `E-base` — not one task with a rubric that the learner has already closed;
- **in code** (R27). The command "whether it changed" is `sim gate changed`. It compares the canonical text of the translated module, that is, exactly what `pack.Translate` takes, with the same of the newest published version that is not withdrawn. The states are `new`, `changed`, `same` and `transition`; in a format transition a module does not run, even when the pull request changes the tag of `sim` (`-all`). The mode `just gate modules` runs the gate on the packages of the pull request: the gate's cells whose graphs are wholly covered by the packages that run, with a repeat for `I1`, then `sim gate thresholds`. `A-linked` runs on both maths from the pull request: `sim gate changed` gives out the unchanged one with the line `along`, and it runs only in the cells that it shares with the changed one (R31). The report names a module on which no population of the gate runs, and the gate does not turn red for it; in the same way it names a cell that lacked the package of the second module of its graph. The form of the call for the job of `modules` is README, "Gate in the CI of modules";
- **what next.** Merged content comes out as a release of `modules`. `sim` pins its packages by a pull request of its own, with new bands and the gate's table before and after (section 3.7), and the libraries take that tag when they need to.

**Time and the runner.** The gate runs on `ubuntu-24.04`: for a public repository it is x64 with 4 CPUs and 16 GB, free, and a job may run for up to 6 hours (sources 2.3). The job's budget is `timeout-minutes: 15`. At first this was an estimate, not a measurement: standalone's guard had 10 minutes, and itself ran for a few seconds (sources 1.1), whereas the gate has, beyond the run, the build of the stage `toolchain` of `sim`, about fifteen cells of 300 learners and the repeat of the run for `I1`. The first code of the gate measures the time on the runner, with a cold build of the stage and with the cache, and the number is corrected by the measurement. The gate's time on the runners is measurements 1.1, in the development container measurements 1.2. By the measurement of pull request #33 (RUN.md, T24) the budget `timeout-minutes: 15` was kept. On `olympiad-math` 0.1.1 the gate on 300 learners did not fit into the budget on the runner, so since T30 it has had 100 learners a cell, and the choice anew on the repeat is taken only for the first 10 (R31). Since T36 the gate's process runs with `GOGC` 400 and on one processor (R33). The gate's size is taken by the slowest measurement at each caller, with 3 minutes of margin before the timeout — `learner-model` and `engine` have no Go cache, and the gate runs longer there. So the gate has 150 learners (the 2026-11-11 amendment to R31). By a recalculation of the slowest measurement on `modules` v0.2.5 and `learner-model` v0.1.6, since T46 the gate has 250 learners (the 2026-11-12 amendment to R31). A gate that does not fit is cut by an edit of `sim`, not by time. The bands do not depend on the architecture: the same bits on any build are held by `learner-model` (R09 learner-model), by the simulator's distributions (section 3.4) and by `engine` — «тот же выбор и тот же код на любой сборке одной своей версии и версии `learner-model`» (R10 engine). So `sim`'s own CI runs the gate on `ubuntu-24.04-arm` too and checks the numbers to the last digit, and for the callers `ubuntu-24.04` is enough. R08 left to the code epic which job does it, and R09 decided it, below. The options of the shared `go.yml` that Д114 in table 4 of RUN.md of `spec` promised came out as one boolean input, `same-bits` (architecture 3.11 spec; the releases of `.github` v0.1.18–v0.1.20, sources 5.2). With it four jobs run: `targets` — the tests at `GOAMD64` v3, at v1 with `cpu.all=off`, on 386 and in js/wasm; `fma-diff` — the assembly of each package with fusion and without it on six targets; `arm64` — the caller's `ci-test` on `ubuntu-24.04-arm`; `rules` — the rules of code by the tool of `.github` with the caller's lists. One cannot take a part of them, and for the simulator they pull in different directions:
- for: if the gate runs in `ci-test`, the job `arm64` runs it on arm64 by the recipe of `sim`, that is, through `go.work` from the gate file; `fma-diff` and the rule `fused` hold the same bits of the simulator's distributions (section 3.4);
- against:
  - `targets` and the second half of `arm64` run not the recipe but `go test ./...` — without `go.work` from the gate file, on the versions of the libraries from `go.mod`, not on the commits where the bands were recorded (above). A gate that checks the chosen versions against the recorded ones is red there, and without the check it measures the wrong thing, so the test at v3 does not check the gate;
  - the simulator does not need the runs on 386 and in WebAssembly — it is not built for a device —, and `targets` runs all the tests four more times, one of them in js/wasm, within `timeout-minutes: 30`, whereas one gate on amd64 is estimated at 15 minutes (above);
  - the rule `math` lets into the code only the exactly defined functions of `math` — `Abs`, `Floor`, `Sqrt` and eleven more —, and the learner's truth needs σ, the power and the exponential laws of retention (sections 3.1 and 3.2) and the normal distribution (section 3.4): the simulator would have to write `Exp`, `Pow` and `Log` itself. The rule `maprange` lets no ranging over a map into the code;
  - the rule `goroutine` lets no goroutines into the code, but lets them into the tests: the simulator could distribute the learners over the cores only from a test.

The other way is a job of its own on arm64, as `go-arm64` of `learner-model` (sources 3.2), and a test at v3 of its own. The risk of `GOAMD64` v3 is held even without them by the same bits of the libraries (R09 learner-model; R10 engine) and by the requirement on the simulator's distributions (section 3.4).

**Decided (R09, 2026-11-08):** both, each for its own part. The simulator's code keeps the input `same-bits: true` on the job "Go" of the shared `go.yml`: `fma-diff` and the rule `fused` check the same bits of the distributions on all targets in advance. The argument against — the rule `math` — is removed by `detmath` of `learner-model`: it gives `Exp`, `Log` and `Pow` with the same bits (R09 learner-model), and `sim` depends on it anyway. There are no goroutines in the code — the decisive run is split into processes by learners, and its recipe splits it —, and no ranging over maps either. The simulator does not need the runs on 386 and in WebAssembly, but they do not hinder it: only the tests of the code, small ones, run in `ci-test`, and the gate and the decisive run do not, so four extra runs of all the tests are a price that the author accepted for the sake of `fma-diff` and the rules. The gate is not part of `ci-test`: in `targets` and the second half of `arm64` it would run without `go.work` from the gate file. It runs as a job of its own in `ci.yml` on `ubuntu-24.04` and `ubuntu-24.04-arm`, in the stage `toolchain` of `sim`, and on both the numbers are checked against the bands to the last digit.

**Releases of `sim`.** A release comes out by itself, after green CI on `main`: the next patch of the line, immutable, and GitHub signs it with an attestation of the tag, the commit and the files (R31 spec). The shared `release.yml` of `.github` v0.1.21 releases it (R29; the 2026-11-09 amendment to R05): "without files" would hold only with a workflow of its own, as in `spec`, and the shared one requires at least one file in `dist/` (sources 5.2). So the release has one file, like the source archive of `engine` (R15 engine): `sim-<version>.tar.gz` — what builds the simulator and runs the gate, signed without a key; `release-verify` accepts it. The line is `0.1`, the first tag `v0.1.0`. A new release comes only from a change of what the gate is built from: the code without tests, the embedded packages and paths, `go.mod`, `go.sum`, `gate.json`, the recipes and the stage `toolchain`. The callers take `sim` from git by tag and SHA (above), not as the archive. The callers' tag is raised by the session of a library or of `modules` — in the pull request that needs the new tag, or by a task of its own. Dependabot will not raise it: it updates references to actions and to reusable workflows of the form `actions/checkout@<commit>` (sources 2.3), and the tag and the SHA of `sim` at a caller are inputs of the checkout step, not such a reference. This is an inference from the documentation, not its words. The first tag comes after the first versions of both libraries (R12 learner-model; R103 spec), and it runs the already published graphs (R76 spec). Before it there is no gate in any CI.

**The order of releases.**
- **A change breaks an API that `sim` is built on.** The library's pull request P is red: `sim` does not build.
  1. A pull request to `sim` edits the simulator's code for P, and the gate file names the last commit of P. Its CI builds the simulator on that commit, through `go.work` from the file; if the numbers did not shift, the bands stay as they were.
  2. Merge, and a tag of `sim` comes out.
  3. P raises the tag and the SHA of `sim` and turns green, then merge.
  4. The library's release comes out.
  5. A pull request to `sim` moves the file to the commit of the release, and `go.mod` to the release itself; the numbers are the same. The next tag comes out.
- **A change of `learner-model` breaks an API that `engine` is built on.** The simulator will not help here: the fix has to be a commit Q of `engine`. This is a pair, and it goes by the order of a pair below, with P and Q.
- **A change moves the numbers on purpose.** This is a candidate, and the criterion judges it (section 3.6): `sim` runs the decisive run and the confirmation on the last commit of P. Then the same steps: a pull request to `sim` records the bands anew, with the reason and the report of the criterion, in review (section 3.7), → a tag of `sim` → P raises the tag → merge → the library's release → the `go.mod` of `sim`. A change of a library that is not a candidate but moves the numbers is the same, with the gate's table before and after.
- **A pair — the threshold "mastered" and the target of the corridor** (section 3.6).
  1. `sim` runs the pair — the last commits P of `learner-model` and Q of `engine` — against the pair of bases. A pull request to `sim` records the bands on both commits, and a tag comes out.
  2. P raises the tag: its gate takes `engine` by the commit Q from the file and turns green. Merge of P, then the release of `learner-model`.
  3. Q raises the tag, and `learner-model` in `go.mod` to that release. Its gate takes `learner-model` by the commit P from the file and turns green. Merge of Q, then the release of `engine`.
  4. `sim` moves the file and `go.mod` to both releases.

  Between steps 2 and 3 `learner-model` has already come out, and `engine` not yet, so the pair is not merged at once. Therefore P is merged only when Q has passed review and its gate at the same tag is green, and `api` moves to both versions together — the review of the pull request of `api` holds this, as with `tutor` and `modules` (repositories 4 spec). If Q is still not merged after the merge of P, `learner-model` rolls back only forward: a new pull request returns the former constant, and `sim` writes the file back to the pair of bases (Т-19).
- **A change of `sim` itself** — a new pin of a package, a population, an edit of the simulator — goes as a pull request to `sim`, with the gate's table before and after if the numbers shifted. The callers stay on the former tag, and it is still green for them: the tag is immutable.
- **A change of content** — the gate of `modules` above, and after the release a new pin in `sim`.

A pull request P that got new commits after the bands were recorded passes the gate if the numbers on its code are the same: the gate checks the numbers, not the commit. If P is closed without a merge, the tag of `sim` recorded on it stays, and the next pull request to `sim` returns the file to the released version. Until the library comes out, the file names a commit that is not in its releases. This is an interim tag, and the callers take it only in the steps above.
