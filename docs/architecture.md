## 1. Purpose and bounds

**Does:**
- runs `learner-model` and `engine` on thousands of virtual learners of different populations: a virtual learner answers tasks, the learner model estimates its mastery of skills, the engine chooses what to give next. In the platform's work `api` passes the graph and the evidence to the libraries, and on the simulator `sim` itself does;
- measures what the platform promises about the learner model and the engine:
  - the success corridor: a task is solved with a probability from 0.70 to 0.85, with the target 0.775;
  - the cautious "mastered";
  - the same input gives the same output, and each choice has a reason code from the closed list `ReasonCode` of the [contracts text](../spec/contracts/README.md).

  On the graphs of all three modules of the first slice: the engine holds the success corridor where there is a verdict, goes by the author's order where there is none, does not get stuck and does not declare "mastered" too early;
- holds the criterion by which a new rule is chosen, and the tolerance bands. The criterion is written down before the first run of a candidate;
- serves as a CI gate:
  - every change to `learner-model` or `engine` is run on the simulator, and a change that worsens the criterion is not merged. How a library's CI takes the simulator is in the gate in CI, below;
  - the CI of `modules` runs `sim` if what the simulator reads from a package has changed — `sim` decides this — on the package of the pull request. There the gate holds invariants and thresholds, not bands.

**Does not:**
- does not change the algorithms but only measures them. The learner model is the business of `learner-model`, the choice of the next lesson or task that of `engine`;
- holds no data of live learners: no answers, no work, no logs of `api`. The virtual learners are synthetic, like any examples in NovaTrail's repositories;
- does not call AI: everything that calls a model is in `tutor`, and code computes the learner model and the choice;
- does not read modules through `module-kit` and does not check them: it reads the packages by the types from `spec`, and `module-kit` checks a module;
- does not work in the platform: it is a CI tool, not a part of the service.

**Data and links:**
- the data are module packages, pinned by version in `gate.json`: from them come the skill graphs, the tasks and the lessons. `sim` reads the server part, `server.json` — the module's canonical view with the tier of each skill and the numbers of each instance of a template, as the [format text](../spec/format/README.md) sets it — by the types `formatv0.CanonicalView` of the Go module `spec`, without `module-kit`. The code takes the Go module `spec` at the tag of the submodule: the module's version and the submodule move together, and the module `spec` is excluded from Dependabot `gomod`. It reads the packages in the same window of format versions as `module-kit`: while the format is v0, only the current version of the format text of the submodule. At stage 1 the packages lie in the releases of `modules`;
- `sim` passes the graph to both libraries in the types of `learner-model`: it sets them, and `engine` takes them from it, so the graph from a package is translated into one form, not two. A function of `learner-model` derives the bands where a skill is taught from the module's skills and task descriptions, and the description of a task is one for evidence and for a candidate task: the band, the difficulty from 1 to 5 within the band, the skills, the items with their answer slots. For the engine a task template is one task, and the simulator chooses the instance by a seed with the same choice as the platform. To the engine the simulator also gives the pool of tasks, the lessons, the lesson runs, the closed attempts of tasks with a rubric and the summary of issues — for a skill, the time of its last issue, where the issue of a lesson is the issue of each of its skills, and, if the skill's last closed attempt was a probe or a repetition, its outcome as facts; for a module, the number of choices, of a task and of a lesson one each; for a task, the time when its solution last went to the device — as `api` gives them in the platform's work. The simulator assembles the summary from its own choices and attempts, as `api` does from its records. It selects the pool and the lessons, as `api` does, by `age_categories` for the learner's age category: this is a filter of `api`, not an input of the engine;
- at build time it depends on `learner-model` and `engine`. The CI of these libraries takes `sim` by a tag — as a CI tool, not as a build dependency, so there is no cycle. The CI of `modules` also takes `sim` by an exact tag. The caller pins the tag and the SHA of the commit of `sim`, and `go.work` puts its code in place, as the gate in CI, below, describes;
- the libraries get the time and the seed from outside: on the simulator `sim` gives them. `spec` sets the generator of randomness and the derivation of seeds, with test vectors — one for the whole platform: `module-kit`, widgets, `engine` and `sim`. With it `sim` derives the seeds of virtual learners, not with a scheme of its own, and it passes its test vectors in CI, with a workflow of its own. The generator is PCG, and the stream of a place of randomness is derived by FNV-1a 64 from the seed and the names of the place, as the [format text](../spec/format/README.md) sets it. The function `seeded` of standalone's simulator is a particular case of this derivation, so the simulator's numbers are kept, and the normal and exponential distributions are not in the format, and `sim` is responsible for their portability;
- the example is `tools/learners` and `docs/learners.md` in standalone (sources 1.1–1.3). MathTrail's code under MIT is carried over freely, and the MIT notice is kept;
- CI: the shared checks of `.github`, `docs-check-repo` among them — `.github` sets which they are and which of them hold the merge —; the job "Go" of the shared `go.yml` with the input `same-bits`; CodeQL for Go; the tests, whose coverage goes to Codecov and holds the merge; the gate and the release, in the gate in CI, below;
- stage 1, together with `learner-model` and `engine`: the simulator needs both the model and the rule of choice, and the simulator and the criterion appear before the first candidate.

## 2. To decide when detailed

Nothing here is open: the card's items of "To decide when detailed" are decided, and so are the questions of the design the libraries and `spec` brought. ### 2.1. Profiles of virtual learners

- **Gist:** which virtual learners the simulator has — how each answers, how its mastery of skills changes, how it studies over time — and on which skill graphs it goes; with them, three more items of the card: forgetting, the weights of evidence and the anchor skill. A population is an assumption about live learners: the simulator does not measure it but takes it. The card's profiles are the populations here: in `spec`'s vocabulary a profile is a learner in an account.
- **Decided:** the virtual learner and its calendar, the populations, the graphs and tasks, and the seeds, each a subsection of the design below.
- **Deferred:** checking the simulator's numbers against live learners — stage 2, when `api` has their data (Д3 of [run/DEBT.md](../run/DEBT.md)). The speeds, laws and shares of the populations are the simulator's assumptions, not a measurement, and are revised with that check.

### 2.2. The criterion and the tolerance bands

- **Gist:** by what rule a new rule of the learner model or of the engine is found better than the previous one, or at least no worse — the criterion — and how far the numbers may shift on each change for the CI gate to let it through — the tolerance bands; with them, the measures of forgetting, of the weights of evidence and of knowing an anchor skill. Both are written down before the first run of a candidate.
- **Decided:** the measures and invariants; the criteria of the model and of the engine on a common basis; the gate and the two-sided bands; the sizes of runs and the seeds — each a subsection of the design below. The paths of the targets are pinned by code.

### 2.3. How the CI of the libraries takes the simulator (Т-16)

- **Gist:** how the CI of `learner-model`, `engine` and `modules` gets `sim`, puts its own code in place and reads the gate; how long the gate takes; in what order the releases come out when a change breaks the API of a library that `sim` is built on, or moves the numbers on purpose; what the gate in the CI of `modules` includes (Т-16).
- **Decided**, and `spec` took it as the answer to Т-16: the caller writes `go.work`; the gate in the CI of `modules` holds everything the simulator reads from a package, with thresholds; the gate file, the releases of `sim` and the order of releases are in the gate in CI, below. The gate gives the same bits on amd64 and arm64.

### 2.4. The small path

- **Gist:** what a judgement does with a measure whose pinned path is positive but no greater than the author's tolerance.
- **Decided:** such a measure leaves the score, as one with a path no greater than zero, and the report names it, as the criteria below describe.

### 2.5. Format 0.4: the check kind `time` and the leading question

- **Gist:** how the simulator reads the check kind `time` and a task's closed leading question, `leading_question`, which the [format text](../spec/format/README.md) brought in its version 0.4.
- **Decided:** a module publishes them only once `learner-model` and `sim` read them, and `sim` reads them: the translation takes `time` as a check kind of its own and, for a task, whether it has a leading question; the truth guesses `time` with the probability 0, and the request of `G8` on a task with a question gives the question too, as the virtual learner, the populations and the graphs and tasks below describe.

### 2.6. The fairness of the learner model by the grade

- **Gist:** a third criterion: virtual learners of the same skill and different grades come to the same estimate and the same kind of task within a number of attempts written down before the first run, and the result goes into `spec`'s DPIA. It is no choice among candidates: it measures the base, and holds candidates to the base.
- **Decided:** the populations `D-`, with their seeds; the measure `M11`; the evaluation of the base and the constraint `fair` of the criteria of the model and of the engine; the 68 cells of a decisive run — each in its subsection of the design below.

## 3. Design

What the section above decided is designed here: first the virtual learners — the learner, the populations, the graphs and tasks, the seeds —, then the measures, the criteria, the gate with its bands and the seeds of runs, and last the gate in CI. `sim` is a program in Go, a CI tool, not a library and not a service: the module `github.com/altnovatrail/sim`, the root is `package main`, and the parts are the packages `internal/<part>`. The pins — the libraries, the release of `modules` and its packages, the module `spec` — are in `gate.json` and `go.mod`.

**The parts:**
- **the learner's truth and the calendar** — the simulator's own model, not the code of `learner-model`: the grade, the starting band, the module level and the skill offsets, a task's hardness with the author's miss, the answer of an item, retention and stability, the hint ladder, the technique and the leading question on request, lessons and tasks with a rubric; days, sessions and breaks — the package `internal/learner`;
- **the populations** — nineteen from standalone and twenty-two new ones, each changing one assumption of the base one, three of fairness by the grade, one learner under three grades, and that of the rules, run only by name — the package `internal/population`; on 44 populations, 68 cells of a decisive run, and the engine's ceiling on the 65 without the three of fairness;
- **the packages** — the server part of the published packages by the types `formatv0.CanonicalView`, pinned in the gate file by the tag of a release of `modules`, the digest of the index and the digests of the packages, and synthetic packages in the form of the three modules, only for code and tests — the packages `internal/pack`, `internal/published` and `internal/synthetic`;
- **the seeds and distributions** — the format's places of randomness, the sets of working and held-out learners and the held-out set of each judgement, its own normal and exponential distributions with the same bits on any build — the package `internal/seed`;
- **the run** — the package `internal/run`: the simulator builds the graph with a function of `learner-model` once per package, from the module's skills and task descriptions, and for the populations `A-` per pair of maths; on each learner it gives the engine the input at the time of the choice — what the model gives on reading, with the flags of the module's trial series, the pool of tasks, the lessons, the runs, the closed attempts with a rubric and the summary of issues, the pool and the lessons by the learner's age category, and, if the rule needs randomness, the seed of choice — gets the choice — a lesson, a task or "nothing to give" — chooses the instance of a template by the seed of the attempt, answers with the truth and passes the evidence to the model; the calendar gives the time. The run is split into processes by parts of the learners, not goroutines. Within a lesson whose skills all have a verdict it calls the engine at the end of each task segment, as `api` will: the lesson of the same run is the next segment and no new choice, a task outside the lesson is a consolidation, given at once, and after it the engine must give the lesson again; any other answer stops the run. On the base the answer is always the next segment, and the step gives the same bits;
- **the measures and invariants** — `I1`–`I4`, `M1`–`M13`, `E1`–`E5` by the truth that the simulator knows, and the note `E6`, which no check reads; `M11` is read off pairs of a grade and the reference, not off a cell of learners; the invariants are the package `internal/invariant`, the measures and the note `internal/measure`;
- **the file of results and the comparison** — the commands `sim run` and `sim compare`, the package `internal/bench`: two versions of one library side by side each write a file of results of their own, and `sim compare` and `sim judge` read them in pairs by learner;
- **the criteria** — the package `internal/criterion`, the command `sim judge` — of the model and of the engine on a common basis, with the base, the ceilings, the path of the targets, the tolerance, the score groups, the confirmation and the exit, and the report of each run in Markdown; the candidate pair. The paths of the targets are pinned by a decisive run in `internal/criterion/paths.json`, which `sim paths` writes, and a judgement takes the path from there; the report of each judgement is in `judgements/<criterion>-<n>/`, where n is the round, and that of a judgement of one variant apart from the rounds in `judgements/<criterion>-<variant>-<n>/`. A judgement embeds `gate.json` and refuses if the base or the base of the confirmation ran not on the libraries of the paths or not on the versions of the gate file, or if a candidate's second library is neither the base's version nor the commit of its pin; so a judgement of `judgements/` is reproduced only on its own commit. ### 3.1. The virtual learner

**Words.** A virtual learner is a synthetic learner of the simulator: it has a truth of its own, which the simulator knows and the learner model estimates by its attempts. A population is a set of virtual learners that changes one assumption of the base population; in standalone it is a "generator" (sources 1.2). In `spec`'s vocabulary a profile is a learner in an account, and a generator is the algorithm that gives numbers from a seed: so here a profile is only in the vocabulary's sense, and the word "generator" is not said of populations. On the simulator each virtual learner, like a profile of the platform, has modules, attempts and lesson runs.

**The learner's truth** is the simulator's own model, not the code of `learner-model`: the simulator measures the model on a learner it knows, not on a copy of the model. The base population holds the model's assumptions, as G0 in standalone holds the assumptions of standalone's model, and each population below changes one of them. In a module of the learner:
- **the grade and the starting band.** In olympiad maths the grade is from 1 to 6, evenly, in grade 3 maths it is 3, and the essays have no grade. The age category is one per learner, as for a profile, not per module: for a learner with a grade it is `under_13`, for `S-adult` `adult`, for a learner of essays one of the module's `audience.age_categories`, evenly. By it the simulator, as `api` does, selects the pool and the lessons. The starting band and its shift 2.5 · (p − 1) are as in the model: the band whose grades name the learner's grade, and without a grade the first. The populations `D-` fix the grade, and shift the truth's level by the starting band of grade 3 whatever the grade, while the model starts by the learner's own;
- **the module level** θ* is the shift of the starting band plus N(0, 1); each skill with the assessability `verdict` has an offset δ* from N(0, 0.5²). This is the base population of standalone, with skills instead of topics (sources 1.2). A learner of two modules has two levels, and the population sets the link between them;
- **a task's hardness** β* = 2.5 · (p − 1) + (d − 3) + miss, where p is the place of the task's band, d its difficulty, and the miss is how far the author erred in the difficulty: 0.5 · z, where z from N(0, 1) is one per task per run. The miss is a property of the task: all the learners of a population see it, and the populations of the miss change only the factor at the same z;
- **the answer of an item.** The item's first verdict is "correct" with the probability P* = c* + (1 − c*) · R̄* · σ(a · (θ* + δ̄* − β*)), otherwise "not yet". c* is the product over the item's answer slots: 1/k for a choice of k options and 0 for the others — for a number, a fraction and a time of day, `time`, as in the model; δ̄* and R̄* are the means over the item's primary skills; the slope a = 1. The items of one attempt are independent given the truth. This is how the model computes P;
- **the retention** R* of a skill is by the model's law, a power law: R* = (1 + F · Δt / τ*)^(−C), C = 0.5, F = 19/81, with the stability τ*, which starts at one day, τ₀. As in the model, a skill's τ* changes at most once per attempt, by the share of correct first verdicts S̄ of the skill in it: τ* := max(τ₀; τ* · (1 + g · (1 − R*))^S̄ · (1/2)^(1 − S̄)), g = 15 — after only correct ones it grows, after only "not yet" it is halved, but not below a day. The truth's stability is moved by the learner's own answers, not by the model's estimate. The module level is not forgotten;
- **learning.** The base population does not learn, like G0; the main population is `G2-half`;
- **the attempt.** The learner answers all the items. After a wrong answer it answers again, on each of the three rungs of the hint ladder, and each rung adds 0.5 to the logit of the items that are not yet correct. From the fourth wrong answer the solution is shown: to a child by an adult action, as by default, and to a learner of the category `adult` by its button. The close reason of the attempt is "correct" or "solution shown". The repeated answers do not count among the 200 answers of a run: the model reads the item's first verdict. It does not ask for a hint by the button, does not take a technique on request, does not abandon the attempt, and it has no "unreadable";
- **a lesson** it goes through segment by segment to the end, and the explanation and the example do not change the truth; a task of the lesson it solves like any other. A task of consolidation that the engine gives at the end of a segment it solves like any other too, and then goes on with the lesson at its next segment; the lesson with its consolidations is one place of the session;
- **a task with a rubric** — in the essays — it writes, submits once and presses "Done": the close reason is "done". It has no verdict and no evidence.

**The calendar.** The libraries get the time from outside, and on the simulator `sim` gives it: days, sessions and breaks, not standalone's "every tenth answer is a new day" (sources 1.2).
- All the learners start on the same day. A day is a session with the probability 5/7, and a session is ten attempts in a row from 15:00 UTC: an item of a sheet takes two minutes, as in standalone, an item line of a workbook a minute, an essay fifteen minutes. The next task is issued at once. The time is whole seconds of UTC, as in the evidence.
- Day 0 of the calendar is 2026-09-07, a segment of a lesson without a task takes two minutes and comes before the lesson's tasks, the answers after a rung of the ladder take no time of their own, a skill's R* before the first attempt is 1, and a skill's last practice is the start of the attempt: these are the simulator's assumptions. A learner has one grade, as a profile does — from the grades that each of its modules with grades names — and one age category — from the categories that each of its modules names.
- A learner's run in maths is 200 answers of items with a verdict, like the 200 answers in standalone; for the populations of forgetting, 180 days of the calendar, so that after the longest break at least 60 days remain; for the essays, until the module's tasks with a rubric that suit the learner's age category run out, but no longer than 60 days.

### 3.2. Populations

Each population changes one assumption of the base population of the virtual learner above; the two sides of one assumption get half of the learners each, by the parity of the learner's number. A population sets the learner, not the rule: what the engine gives `engine` decides, and the populations are the same whatever rule of repetition, of lessons and of the anchor skill at "does not know" it chooses. Which measures are read on which population, and which of them are targets, the measures and the criteria below say.

**The main population is `G2-half`**, as in standalone: a learner that grows by one logit in 200 answers. The main population is for both maths; the essays have no verdict, and there is no main population there.

### 3.3. Graphs and tasks

- **Published packages.** The criterion and the gate run on the published packages of the three modules of the first slice, pinned by version: the simulator names the release of `modules` by the tag and the digest of the index, and each package by the module ID, the version and the digest, and reads its server part by the types `formatv0.CanonicalView`. The release is embedded in `sim` itself — the package `internal/published` —, and the package `internal/pack` reads and translates it. A file of a release of `modules` enters the code or CI of `sim` only after `release-verify`. A new version of a package on the simulator is a new pin, that is, a change of `sim`, by a decision. The pin — the release, and each package's version and digest — is `gate.json`; a package's archive lies in the folder of the release its entry of the index names, which may be an earlier one. While the format is v0, the platform reads only the current version of the format text.
- **Synthetic packages.** `sim` also has synthetic packages of its own, in the form of the three modules — a sheet with choices, numbers, `predicate` and the time `time`, with leading questions and three bands of grades 1–6; a workbook of one band of grade 3 with pages of up to ten items and a skill that teaches an anchor skill; and essays with a rubric, without grades —, and a graph where a skill of another module rests on an anchor skill. This is a canonical view that the simulator assembles, not the content of `modules`: for the code and the tests of the simulator, not for judging candidates. There are no learners' data in them. In code it is the package `internal/synthetic`, with the module IDs `synthetic/…`, which the criterion and the gate reject, and the anchor skill of the shared taxonomy `core.multiplication-table`, which the workbook teaches and on which the sheet's skill rests; the views pass the format's schema of the canonical view.
- **The graph** for both libraries is built by the simulator with a function of `learner-model`, from the skills and the task descriptions of the module, in the types of `learner-model`, as the data and links above say.
- **The task.** The band and the difficulty give the model's β and the truth's β*; the check kind and the number of options of each answer slot give the truth's c* and the model's c; the simulator reads the leading question only as the fact that the task has one — the request of `G8` gives it. The simulator chooses a template's instance by the attempt's seed with the same choice as the platform: the place with the names `template`, the task ID and `instance`, as the [format text](../spec/format/README.md) sets it. For the engine a template is one task, and a template has one miss for all its instances.
- **The miss.** In standalone a chat model wrote the task, and the miss was drawn at every issue (sources 1.2). In NovaTrail the author writes the task, and the author's error in difficulty is one per task: the simulator draws z once per task and run, and the miss is a multiplier of z — 0.5 in the base population, 0, 0.25 and 1 in `G0-exact`, `G0-miss0.25` and `G0-miss1`. So all the learners of a population see the same task, and the populations of the miss see the same error of the author to another degree, as in standalone, where a population's spread is a multiplier of the same numbers. `G4-band` adds a shift of the band to the miss. No fields of the format are needed for this: the miss remains an assumption of the simulator, as does its spread.

### 3.4. Seeds

- **Places of randomness.** Every number of the simulator comes from a place of randomness of the format: the run's seed and names, as the [format text](../spec/format/README.md) sets them. The names are the experiment, the unit and the purpose, so `seeded` of standalone's simulator is a particular case. The unit of a virtual learner is `<population>/<number>`, the unit of a task `task/<module ID>/<task ID>`, with the purpose `miss` for its z. The learner's purposes:
  - `params` — the learner's truth: the grade, the level, the offsets, what the learner's population differs by, the band of `G4-band`;
  - `calendar` — the days, the sessions and the breaks, and which day is bad in `W-badday`;
  - `answers` — the first answers of items: the learner's k-th first answer takes the same numbers in the same order whatever happens, as in standalone, so the learner meets the same numbers under any rule;
  - `retries` — the answers after the rungs of the ladder and the answer the learner writes again after "unreadable": a stream of its own, so that the repeats under one rule do not shift the first answers;
  - `attempts` — the learner's k-th attempt takes the same numbers in the same order: the shift of `W-shock`, the error of `W-error`, the technique of `G8`, the segment where `L-abandon` abandons the lesson, and the leaving of `E-leave`;
  - `attempt` — the seed of each attempt, for the instances of templates;
  - `choice` — the seed of the engine choice, if the rule of `engine` needs randomness. The first version of the rule takes no randomness, and the seed of the choice is empty: the purpose stays reserved by the simulator in case a new version takes randomness.
- **Populations do not shift one another.** A new population is new names of units, and the numbers of the learners of other populations stay as they were, as in standalone (sources 1.2). The populations `D-` are the one exception to "a unit a population": all three take the unit of their reference, `D-grade3/<n>`, for every purpose, so the learner n of each grade is the same learner; in code it is `Population.Units()`.
- **Working and held-out learners.** The held-out learners take a seed of their own and a name of the experiment of their own: the format says to take a seed of one's own when streams must stand apart from others' ("a use that needs streams apart from another's takes a seed of its own", the [format text](../spec/format/README.md)). A test of the code shows that no learner is drawn alike in two sets, as in standalone, and on the held-out learners a choice is confirmed once. The seeds themselves are in the sizes of runs and seeds, below.
- **The normal and the exponential distributions** are the simulator's own: the format does not give them, and the simulator builds them on `fraction`. What is required of them is the same bits on any build of one version, as in `learner-model`: otherwise the gate's bands would part in the last digits on another processor (sources 1.1). The normal one is the inverse distribution function by AS 241 on one `fraction`, with `detmath.Log` and `math.Sqrt`, the exponential one is `0 − ln(1 − u)` with `detmath.Log`, and every product goes through `float64()`; the golden bits are held by a test on all the builds of `same-bits`. The place of randomness is the package `internal/seed`; the gate's runner is in the gate in CI, below.

### 3.5. Measures

A measure is read from the learner's truth, which the simulator knows, and from what `learner-model` and `engine` gave. The simulator has three layers of checks: the invariants, which hold on every learner; the measures, of which the criteria below are made up; the gate's numbers with bands, after them. The names of the measures are for the simulator's reports and for the bands, as the names of `cells.csv` in standalone (sources 1.2).

**True mastery.** A skill is mastered by the truth at a band when the P* of the reference task — of difficulty 3 at that band, without a miss, with a choice of five options and at R* = 1 — is at least 0.775, the middle of the corridor. This is standalone's "truly mastered" (sources 1.2): the same answer at a guessing of 0.2. The reference does not depend on the threshold of the model of `learner-model`, 0.71875, though at this guessing it coincides with it: the truth does not read the model's numbers. The truth "knows" an anchor skill when at least one skill that teaches it is mastered by the truth, with R* at the time of reading — so with the truth knowing fades, and with the model it does not. The population `A-fading` reads true mastery the same way.

**Invariants** have a tolerance of zero: one violation on one learner is a red run, and a red gate too. The package `internal/invariant` holds them; `I2` checks the meaning of a code by the facts that it names, and the order of "longest" and reachability belong to the rule of `engine`.

| Name | What holds |
|---|---|
| `I1` reproducibility | A run repeated on the same seeds gives the same bits of every choice, of every piece of evidence, of the model's state at the end and of every number of the measures — the state after each step follows from the evidence, and the same bits of the evidence and of the final state hold it too; a choice repeated from the input that it stores is the same choice, each call of the engine within a lesson too |
| `I2` reason code | Every choice has exactly one code from the closed list `ReasonCode`, and "nothing to give" has no code ([contracts text](../spec/contracts/README.md)). The code is true to its meaning on what the simulator knows, by the facts that it names, on a skill with a verdict, except "the author's order": "new skill" — the skill has not been issued yet; the rule counts its prerequisites as met — they are mastered, or the input has nothing to teach them with — or it has none, and at "the bottom of the ladder" the rule gives it without them too, and that part is held by the golden vectors of `engine`; "consolidation" and "probe" — only a task; "repetition" — the time of the choice is no earlier than the model's review date; "consolidation" — the previous attempt on this skill had a wrong answer, and the module's last evidence is no longer in the trial series; "the queue" — the skill has gone unissued for longest in its module among the reachable ones that were issued before and are not mastered, by the summary of issues; "probe" — not in the module's trial series. The simulator reads the trial series by the flags that `Read` returns; "in rotation" — a skill that was issued before and has gone unissued for longest, but does not fit "the queue": it is mastered, or there are no reachable skills (`REASON_CODE_ROTATION`); "the author's order" — a skill with a rubric or without assessment; "the lesson of an open run" — the run is open. The simulator's learner does not open the skill map, and "the learner chose the skill" never occurs on the simulator |
| `I3` the author's order | For skills with a rubric the choice goes to the next one by the skill graph, without the learner model |
| `I4` repeat of the solved | A task, not a template, whose solution has already gone to the device is not issued as the next task: `spec`'s rule that a seen solution is not given again "at once" means "not as the next task". Beyond that it is the pause of `engine`, not an invariant: 24 hours, except on the second pass, when the choice otherwise gives nothing |

| `M11` fairness by the grade | The learner n of a grade against the learner n of the reference `D-grade3`, on the module level θ after each answer: `M11.answers` — the answers until \|θ − θ of the reference\| holds below 0.5 for ten answers in a row, counted as `M3` counts, the mean over all, a learner for whom it never holds counting as 200; `M11.same` — the share for whom at most 50 answers go before the series, so that it holds from the 51st answer at the latest; `M11.band` — the largest absolute difference, over the three bands, between the grade's and the reference's shares of the attempts with a verdict at that band, from the 51st answer to the end, the tasks of lessons and consolidations among them. The resamples are of n, the same in the three cells | `D-grade1`, `D-grade5` |
| `M12` the guard's false firings | `M12.false` — the share of the learners of the reference `D-grade3`, whose truth is the band of their grade, on whose run the guard of `learner-model` lowered the module level at least once, read off the field `guard` of the trace | `D-grade3` |
| `M13` at the truth | `M13.answers` — the answers until \|θ − θ*\| holds below 0.5 for ten answers in a row, θ the model's module level and θ* the truth's after each answer, counted as `M11` counts, 200 when it never holds; `M13.same` — the share for whom that is at most 50. Read in pairs of `C-grade1` and `D-grade1`, the adult's correction against the same learners without it | `C-grade1`, `D-grade1` |

In code the measures of the model are the package `internal/measure`: a learner's run gives sums, and a cell's number and its interval are read from the sums of all its learners; what a measure reads about an attempt — the P and P* of the items, P without retention, the pause, the module's skills before and after — the run records as an observation, `run.Obs`. "The answers of a skill" are the items of attempts from which the model took evidence of the skill; a pause of a skill is an attempt that answered the skill after 14 days without practice; the help of `M2` is a technique on request and a repeat: the rungs of the ladder come after the first verdict; the truth of the measures is the one that answers, with the drop after the break of `F-break`, but without the bad day. For `M11` the run records the band of each attempt, `run.Obs.Band`, and the line of a learner of `D-` its trace under the engine — the module level after each of the first 200 answers and the attempts at each band after the 50th, `measure.Traced`; `bench.Fair` pairs each grade's cell with the reference's learner by learner, and the numbers, `measure.FairNumbers`, are read off the pairs with the resamples of the reference's cell, so the same n in all three cells.

**Measures of the engine.** An item is one with a verdict; P* is the truth at the time of the issue, with retention.

| Name | How it is computed | Populations |
|---|---|---|
| `E1` corridor | The share of the issued items with P* in 0.70–0.85, below 0.50 and above 0.95, and the pool's ceiling — the mean over issues of the largest share of items with P* in the corridor in one reachable task of the pool that the rule could give — with the same exclusions as for the engine's ceiling, below: the engine chooses a lesson or a task as a whole, not an item, so no rule will rise above it | all with a verdict |
| `E2` being stuck | The share of learners who have 50 choices in a row on one skill without a change of its "mastered" while the pool has another reachable skill, and the share of "nothing to give" with a non-empty pool | all |
| `E3` repetitions | The true R* of a skill when the engine gives it as a repetition, on average; the share of repetitions where the P* of the reference task of the mastery band is already below 0.775 — the lateness; the share of repetitions among the choices by weeks of the calendar (a proposal of `learner-model`); the mean R* of the skills mastered by the truth on the last day of the run | `F-` |
| `E4` coverage | The share of the reachable skills that were issued at least once, and the share of the skills mastered by the truth by the end of the run. The truth grows from the choice only through which skills the learner answers, through the stability τ* and through the lessons of `L-explain`, so coverage is what the choice moves the truth by | `G2-half`, `G2`, `L-explain` |
| `E5` essays | How many tasks with a rubric the learner wrote by the end of the run, and how many times the learner was given a task that they had already closed | `E-base`, `E-leave` |
| `E6` consolidation in a lesson — only the note | On the lessons whose skills all have a verdict: the consolidations in a lesson a pass; the shares of the items of the lessons' task segments and of the consolidations with P* when given in 0.70–0.85, below 0.50 and above 0.95, as `E1` counts them; the mean P* when given of the next task segment after a segment that failed on a skill of the lesson. No check, path or weight reads it: it is the note of a judgement | all with a verdict; a consolidation only on olympiad maths |

In code the measures of the engine are the same package `internal/measure`. What the truth says about the pool at a choice — the ceiling of `E1`, whether there is anything to give, the reachable skills — the run records before the engine choice, `run.Pool`. A skill's reachability is by the truth: the truth holds its prerequisites, and the pool has a task on it that the rule could give. The P* of an issue is the truth's chance without what only the attempt holds. A task of consolidation within a lesson is a choice like any other, with its pool read at the end of the segment; the lesson going on after it is no new choice: it has no pool, `E1` counts its items and not its ceiling, and `E2` and `E3` pass it by. The note `E6` is `measure.Note`, written into a line under the rule `engine` alone, so the ceiling's file has none of it. A consolidation is the task right before the lesson resumed, and a failed segment is read by the results the step keeps beside each attempt, `Step.Results`.

The engine's criterion reads the false "mastered" of `M4` and the lag of `M3` too: which tasks the engine gives moves the estimate as well.

### 3.6. Criteria

Two criteria — of the learner model and of the engine — on a common basis. They are written down before the first run of a candidate, so that a candidate's numbers do not influence what it is judged by.

**The common basis.**
- **A cell** is a rule, a population and a graph. The rules of a run are the base, the candidates and the ceiling. **The base** is the first released version of each library, and after a confirmed choice, what was chosen; outside an interim tag of the order of releases, below, it is the release that `gate.json` and `go.mod` name. Of the first two judgements — of the model and of the engine — the one whose candidates are ready first goes first, and the second runs the base anew, with what the first chose; the path stays pinned. **The model's ceiling** is the oracle: its estimate is the truth θ* + δ*, its P is P*, and it sets "mastered" by true mastery; it is the ceiling of every model that learns of a learner from answers, and for the rule of "mastered" the ceiling is perfection: not one false one, and without waiting, as in standalone (sources 1.1). **The engine's ceiling** is a choice with the same model but by P* from the same pool: the task with the largest share of items whose P* is in the corridor, and on a tie, the one whose mean P* of the items is closer to 0.775, since the engine chooses a task as a whole, not an item. The ceiling's pool has the same exclusions as the rule's: a task with a seen solution — not as the next task, and after the pause of `engine`, with the second pass, or the ceiling would take tasks that the rule has no right to give; a repetition — when the P* of the reference task falls to 0.775.
- **In code**: the oracle is read on the answers of the same run as the model — `measure.Oracle`; the recipe `just decisive` runs a candidate's decisive run with `CANDIDATE_LEARNER_MODEL` or `CANDIDATE_ENGINE`, and a pair's with both and `CANDIDATE_PAIR=yes` — by a commit by its full SHA or by a folder without uncommitted changes —, and the simulator is built through the gate's workspace, and the base by `go.mod`; the recipe `just rough` runs a rough look the same way, on fewer working learners; the engine's ceiling is the run's rule `run.Ceiling` on the pool `run.Pool`, and where the pool gives no task with P* — tasks with a rubric, lessons, "nothing to give" — `engine` chooses; each build writes a results file of `sim run` — JSON Lines, a line per learner, with the version or the commit of each library —, and `sim compare` reads two files in pairs by learner, `measure.ReadPair`.
- **The judgement**: the criteria are the package `internal/criterion` and the command `sim judge` with a judgement file that names the runs of the base, of the candidates and of the confirmation. The judgement file, the report of `sim judge` and the SHA-256 of the runs lie in the repository, in `judgements/<criterion>-<n>/`, and a decision of the log records the result. The judgement takes the path of each measure from the pinned file of paths, not from the judgement's runs, so it needs no run of the ceiling. A check stands where the base reads the number; the path of `E1` in the model's criterion goes to the engine's ceiling; the report names a decisive run or a rough look, and the graphs of the choice. The judgement refuses whole a run that is not of this judgement: the base and the base of the confirmation run on the libraries on which the paths were read and the gate pinned — `sim` embeds `gate.json`, as it does `paths.json` —, and a candidate of one library, and the same candidate on the held-out learners, run on the base's second library: at its version or at the commit of its pin, as the recipe of the decisive run builds it. A pair has no second library. The confirmation runs only on the held-out learners of its own judgement: the judgement file names its judgement, as its folder, and the judgement takes the set that the table of `internal/seed` records for it, so a set kept for another round or variant, or one another judgement has looked at, is refused. The report also writes for each candidate the note of consolidation in a lesson, `E6`, which decides nothing; and a candidate may name in the judgement file, as `equal_on`, the graphs on which it gives the base's runs — the constraint `neutral`, every learner's sums the base's to the bit.
- **The numbers** are over all the learners of a cell, with a 95 % interval from 2,000 resamples of the learners. A comparison is the difference of two cells on the same learners, with an interval from the same resamples in both. Cells of the same learners are runs with the same seeds, and a pair is compared learner by learner: two versions of one library do not go into one Go build, so each runs in a build of its own, through the gate's workspace, and `sim compare` reads their results files.
- **A decisive run** is 2,000 learners a cell, on the working learners. A smaller run is a rough look: its report and its outcome are named so, and it decides nothing; the recipe `just rough` runs it.
- **"No worse":** the worse end of the 95 % interval of the paired difference with the base is within the tolerance. The tolerance is the larger of the author's tolerance and the simulator's resolution: 4.3 standard errors of the paired difference of the candidate and the base on this check, in the same run. So a candidate equal to the base passes the check 99 times in 100, and dozens of checks do not fail it by chance. The standard error is the noise of the comparison on these learners, not the level of the candidate's numbers; standalone read it on a pair of rules already on its simulator, and `sim` has no such close pair. The author's tolerances are a proposal made in execution: 0.01 logit for `M1`, `M3` and `M7`; 0.002 for Brier and 0.01 for the bias of `M2`; 1 percentage point for `E1`, the shares of `E2`, `E4` and `M3`; 2 points for `M4`, `M6` and `M9`; one answer for the counts of answers of `M3`, `M5` and `M6`; 0.01 for R* and 2 points for the lateness of `E3`; one task for `E5`.
- **Direction.** In the criterion every measure goes so that less is better: a signed measure by its absolute value, as `|r6_lag|` in standalone (sources 1.2) — the bias of `M1` and `M2`, `M3` —, the error of `M7` by the root mean square; a share where more is better by its shortfall from one: the share in the corridor of `E1`, the R* of `E3`, the shares of `E4`. So the check "no worse" and the path read the same way for all the measures.
- **Targets** are a share of the path from the base to the ceiling. The path is the base's value minus the ceiling's value, both in this direction; the share that a candidate closed is the base's value minus its value, divided by the path. The base gets 0, the ceiling 1. The values of the base and of the ceiling that make up the path are read on the decisive run of the base before the first candidate, and anew when what they were read on changes: the graph and the tasks of the pinned packages, the base or the size of the decisive run — a new version of the base's library with the same numbers too, since the judgement holds the base to the libraries of the paths. A deferred judgement leaves them; a pin of packages on the same libraries that does not shift the base's numbers leaves them, and so does an edit of the simulator that keeps them; a key of the base's file that no path reads changes only the SHA-256 that `paths.json` names. They are pinned: this is calibration, not a choice, as c* in standalone (sources 1.2). A path no greater than zero — the ceiling no better than the base — leaves the share of that measure unread: the measure leaves the score together with its weight, the report names it, and the target on it is not met. A measure whose path is positive but no greater than the author's tolerance of that measure leaves the same way: a ceiling no farther from the base than the tolerance sets no path, and for a measure with a path to perfection, neither does a base no farther than the tolerance from it; the report names such a measure separately. For the measures where the ceiling need not be better, the path goes to perfection: not one false one, no waiting, no lateness, all the skills mastered. **In code**: the paths are pinned by the file `internal/criterion/paths.json`, embedded in the simulator. `sim paths` writes it from the decisive runs of the base and of the engine's ceiling: the base's value, the ceiling's value in the criterion's direction and the path of each measure of the score groups on each cell of a published graph. What the values were read on is the file's own `libraries`, `set` and `learners`; their measurement is measurements 3.2. The judgement takes the path from this file at every choice and in every confirmation: a candidate's share is its paired difference with the judgement's base divided by the pinned path.
- **A number that the run did not read** leaves the constraint unmet and the score unread. The exception is a graph whose package is not published yet: its checks stand in the report as "no graph", neither met nor failed, and the choice names the graphs on which it was made. A new published package is a new pin in `sim` and new bands of the gate, and earlier choices are not revisited by themselves.
- **Better:** a candidate is better than the base when the interval of its score is above zero, and better than another candidate when the interval of the paired difference of their scores is above zero. The score is the weighted sum of the paired differences with the base at the pinned path; its interval is from resamples of the learners of each population separately.
- **The choice:** among the candidates that hold all the constraints and are better than the base, A* is the one with the largest score, and its equals are those whose difference with A* holds zero in its interval. The simplest of them is chosen: with the smallest number of changed constants, then without a new field in the model's state or in the engine's input, then the closest to the base.
- **The confirmation:** the chosen candidate is run once more, one time, on the held-out learners of this choice, by a decisive run, beside the base; the path is the pinned one. There too it holds all the constraints and is better than the base. If not, it is the exit: no second candidate is tried on the same held-out learners, because a set that has been looked at is no longer held out.
- **The exit:** if no candidate passed or the chosen one was not confirmed, the base stays as it is.

**The model's criterion.** It judges a change of `learner-model`: the step and the uncertainty, "mastered", the scale of bands and the start, guessing, forgetting, the weights of evidence, the anchor skill. Its rounds are the judgements `model-<n>`, each with its outcome in the log; the next is `model-3`, with its confirmation on `held-out-model-2`.
1. **Constraints** — each holds:
   - the invariants `I1`–`I4`;
   - the floor of the first slice — "mastered" is not declared too early: false "mastered" of `M4` at most 20 % on `G0` and `G0-skills1`, and the number of answers before "mastered" of `M6` at most 1.5 times the base's, on the same populations, as in standalone's choice of "mastered" (sources 1.2);
   - "no worse" than the base — on every population with a verdict: `M1` after 200 answers, `M2` Brier, `M4`, `M6` — the share not declared, `E1` — the share in the corridor; on their own populations — `M3`, `M5`, `M7`, `M8`, `M9`, `M10`, `E3`;
   - `fair` — fairness by the grade no worse than the base, below;
   - the targets — for a candidate that names them as its target, as the step in standalone: on `G2-half` the lag of `M3` closes at least 0.55 of the path to the oracle, and the corridor of `E1` at least 0.27; on `G3` the share not caught up after the jump is at most 25 %. These are standalone's targets written as a share of the path: the lag at most 45 % of the service's, and c* = 0.27 (sources 1.2). A candidate with another target holds the floor and "no worse", and its target is its score group below.
2. **The score** is the share of the path from the base to the oracle, averaged over the measures of a population, weighted by populations and groups. A candidate names its group, and the interval of that group's score is above zero too: an improvement where the candidate promised it.

| Group | Weight | Populations | Measures |
|---|---|---|---|
| Stays put | 1 | `G0` | `M1` after 200 answers; the shortfall of `E1` |
| Learns | 2 | `G2-half` 1.25, `G2-fading` 0.5, `G2` 0.25 | the absolute value of `M3`; the shortfall of `E1` |
| Changes at once | 1 | `G3` 0.4, `G3-drop` 0.4, `F-break` 0.2 | the number of answers until catching up of `M3` |
| Out of its band | 0.5 | `G1` 0.375, `S-adult` 0.125 | `M7` after 10 answers; the share of hard first items of `M7` |
| "Mastered" | 1 | `G0` 0.5, `G0-skills1` 0.5 | `M4`; `M6` — the number of answers before "mastered"; the path — to perfection |
| Forgets | 1 | `F-model` 0.4, `F-exp` 0.2, `F-C1` 0.2, `F-growth5` 0.2 | Brier of `M2` after pauses from 7 days; `M5`; `M4` after a break |
| Pages | 1 | `W-shock` 0.5, `W-error` 0.25, `W-badday` 0.25 | Brier of `M2` by the items of pages; `M4` from one or two pages |
| Anchor | 0.5 | `A-fading` 0.25, `A-unpractised` 0.25 | `M9`; the path — to perfection |

A population's weight is a share of the group's weight: the weights of a group's populations sum to its weight, as in "Learns" in standalone, 2 = 1.25 + 0.5 + 0.25 (sources 1.2). The first four groups and their weights are as in standalone's choice of the step; in "Changes at once" and "Out of its band" `F-break` and `S-adult` are added to its populations, and the shares of `G3`, `G3-drop` and `G1` are reduced for them. The new groups and their weights are a proposal made in execution.

**The engine's criterion.** It judges a change of `engine`: the corridor, prerequisites, consolidation, the queue, probes, repetition, lessons, the anchor skill under "does not know".
1. **Constraints:**
   - the invariants `I1`–`I4`;
   - being stuck, `E2`, no more than the base's, with the tolerance;
   - "no worse" than the base — `E1` on every population with a verdict, `M4` and `M3` where the model's criterion reads them, `E3` on `F-`, `E4`, `E5` on `E-`, `M9` on `A-`;
   - `fair`, as in the model's criterion: the engine chooses the kind of task, and its choices move the estimate too;
   - the target — the score group that the candidate names as its own: the interval of its score is above zero. The engine has no number for the target: standalone's c* = 0.27 is a share of the path to the model's oracle in the choice of the service, and the engine's path goes to another ceiling, and carrying the number over would mean making up a number.
2. **The score** is the share of the path from the base to the engine's ceiling, and where there is no ceiling, to perfection:

| Group | Weight | Populations | Measures |
|---|---|---|---|
| Corridor | 2 | `G2-half` 1.25, `G0` 0.5, `G2` 0.25 | the shortfall of `E1` |
| Repetitions | 1 | `F-model` 0.5, `F-exp` 0.25, `F-growth5` 0.25 | the lateness of `E3`; the shortfall of R* on the last day of `E3`; the path — to perfection |
| Coverage | 1 | `G2-half` 0.75, `L-explain` 0.25 | the shortfall of the share of skills mastered by the truth by the end, `E4`; the path — to perfection |

The populations' weights are shares of the group's weight, as for the model. The engine's ceiling gives the path only for the corridor: a choice by P* holds the corridor, but need not cover more skills or repeat on time. The weights are a proposal made in execution.

**The judgement of consolidation in a lesson** judges a variant of `engine`: at the end of a task segment of a lesson whose skills all have a verdict, a task of consolidation outside the lesson after a failure. It was written down before its first candidate:
- **the criterion** is the engine's criterion above, unchanged, and the variant's target is the group `corridor`. `I2` does not change: the previous attempt on the skill of a consolidation is the failed segment;
- **the note** `E6` stands beside the verdict of each candidate, on the cells where the base or the candidate consolidated. It explains where a shift of `E1` comes from and decides nothing;
- **the constraint `neutral`**: the judgement file names, as `equal_on` of the candidate, `novatrail/grade-3-math` and `novatrail/english-essays`, where the variant has nothing to give — in the first all the tasks are in lessons, and the skills of the second have no verdict. On each of their cells every learner's sums are the base's;
- **the order**: on the base after `model-2`, as a separate judgement of the engine and before the round `engine-2`, in `judgements/engine-lesson-1/`, with its confirmation on its own held-out learners, `held-out-engine-lesson-1`. `held-out-engine-1` stays with `engine-2`. The judgement ended in an exit before any confirmation, so `held-out-engine-lesson-1` is still held out.

**Fairness by the grade** is an evaluation of the base for `spec`'s DPIA and a constraint of both criteria. It was written down before its first run:
- **the evaluation**: the base holds when, for grades 1 and 5 alike, `M11.same` is at least 0.90 at the lower end of its 95 % interval and `M11.band` at most 0.05 at the upper end; `M11.answers` is reported with its interval and no bound. A base that does not hold is recorded as it is, and the numbers are not changed afterwards. The base is evaluated anew whenever it moves, by the task that moves it;
- **the constraint `fair`**, a check kind of its own beside `neutral`, holds the model's criterion, the engine's criterion and a pair, at the choice and in the confirmation. On `D-grade1` and `D-grade5` the shortfall of `M11.same`, `M11.answers` and `M11.band` are each "no worse" than the base, as above, less being better. The author's tolerance is 0.01 for the shares and one answer for `M11.answers`. `M11` is in no score group, has no path and no target, save the target of the judgement `model-fair-1` below; a run without the cells leaves `fair` unmet; and the cells `D-` are read by `fair` alone, and in `model-fair-1` by its target too — the checks "no worse" on every population, the floors, `neutral`, the score and the note `E6` are those of the 65 cells. **In code**: the check kind `"fair"` of `sim judge`, three checks on each of `D-grade1` and `D-grade5` — `M11.same` by its shortfall, `M11.answers` and `M11.band` as they are —, once in a pair; the pairs of `bench.Fair` of the candidate against the base's, resampled by the reference's cell, as the evaluation reads them, and each number held by the same function as "no worse". When neither run has a grade's cell, its three checks fail; a candidate whose cells `D-` are not the base's refuses the judgement, the cells of both named; the report names the cell and the number where `fair` does not hold;
- **the report** of an evaluation lies in `evaluations/fairness-<n>/`, n from 1, not in `judgements/`: an evaluation chooses nothing. It holds the evaluation file with the SHA-256 of the run, the criterion in a paragraph, as written down before its first run, the versions of the base and the tag of `sim`, the numbers of grades 1 and 5 with their intervals, whether the base holds, the date and the paragraph for `spec`'s DPIA, which goes to `spec` as a row «в реестр spec». The command `sim evaluate <evaluation file>` writes the report, `report.md`, off the run the evaluation file names — `evaluation`, `run`, `sha256` and `date` — and refuses a run of another SHA-256; it reads only a whole decisive run of the base under the engine, on the working learners and the libraries of the gate file, with its invariants recorded. An evaluation's outcome is its report and an entry of the log.

**The judgement of the round of fairness** judges the round of `learner-model` aimed at the fairness by the grade. It was written down before its first candidate:
- **the criterion** is the model's criterion above, unchanged: `I1`–`I4`, the floors, "no worse" on the 65 cells and `fair` on `D-grade1` and `D-grade5`, which keeps each grade from getting worse;
- **the target** is `M11.same` of both grades pooled: Δg is the candidate's `M11.same` of grade g less the base's — the share as it is, more being better, the opposite sign of the shortfall `fair` holds —, each read off the pairs with `D-grade3` of its own side, and the target's score is (Δ1 + Δ5) / 2, a share of learners with no path, its 95 % interval from the same 2,000 resamples of n as `fair`'s, the same n in both grades and both sides, by the reference's cell;
- **"better"** is the lower end of that interval above zero, and the target alone decides it and the choice — A* by the largest target's score, its equals and the simplest as above. A candidate names no score group; the model's score on the 65 cells stands in the report as a reference and decides nothing;
- **the bounds of the evaluation of fairness** are no condition of the choice or of the confirmation: the report writes `M11` of the candidate and of the base on both grades, Δ1, Δ5 and the target's score with their intervals, and, for the confirmation of the chosen one, whether it holds the bounds; the outcome goes «в реестр spec» for `spec`'s DPIA, and the base moved to the chosen one's release is evaluated anew, `evaluations/fairness-2/`;
- **the order**: deferred while there are fewer than 100 children; when it returns, on the tag and the base that the log is to name before its first candidate, in `judgements/model-fair-1/`, with its confirmation on its own held-out learners, `held-out-model-fair-1`. `held-out-model-2` stays with `model-3`; the target is the table `targets` of `internal/criterion`.

**A candidate pair.** A change of two libraries at once — a new constant of the threshold "mastered" of `learner-model` together with a new target of the corridor of `engine` — is run as one pair against the pair of bases on the same learners. The pair holds the constraints of both criteria and is better than the base by the score of the library whose target it names, and the interval of the other's score does not lie wholly below zero. How the gate runs a pair when a pull request substitutes one library is the gate in CI, below: the gate file names both commits.

### 3.7. The gate and the bands

The gate is standalone's guard (sources 1.1): it does not choose the rule but holds what the rule was chosen for. It runs on every change of `learner-model`, `engine` and `sim` itself — on the commits of the libraries that the gate file names, with the change's code substituted, as the gate in CI, below, describes. In the CI of `modules` the gate holds invariants and thresholds, not bands: an edit of content moves the numbers by design.
- **Learners:** the first 250 working learners of the gate's populations, on each published graph where the population runs: `G0`, `G1`, `G2`, `G2-half` and `G3` on both maths; `F-model` on both; `W-shock` on school maths; `A-linked` on both together; `E-base` on the essays. The run of each learner is as in a decisive one: 200 answers in maths, 180 days in `F-model`, until the end of the tasks with a rubric in the essays.
- **Invariants** `I1`–`I4` — on every learner of the gate; `I1` by a repeat of the run. The gate takes the choice anew at every step only for the first 10 learners of a cell: the repeat holds `I1` to the bit, and choosing anew for all would double the engine's work; the first 10 catch a rule that changes its input in place the same way in both runs. In the same way — only for the first 10 — the decisive run, which has no repeat, takes the choice anew too.
- **The gate's numbers:**
  - `G0` — `M1` after 200 answers, the share in the corridor of `E1` and the share of items with P* below 0.50, `M4`, the number of answers before "mastered" and the share not declared of `M6`;
  - `G1` — `M7` after 10 answers;
  - `G2` and `G2-half` — `M3`, the share in the corridor of `E1` and the share of items with P* below 0.50;
  - `G3` — the share not caught up after the jump of `M3`;
  - `F-model` — Brier of `M2` after pauses from 7 days, `M5`, the lateness of `E3`;
  - `W-shock` — `M4` from one or two pages;
  - `A-linked` — `M9`, on both maths together;
  - `E-base` — `E5`;
  - on all — the share of learners stuck of `E2` and the share of "nothing to give" with a non-empty pool.
- **A band** is the recorded value of a number and half the width of its 95 % interval, from the same resamples. A number is in its band when it is no more than two half-widths from the recorded one, the edges included. The gate's learners are always the same, so code that shifted nothing reads the recorded numbers to the last digit: a band is room for a change, not for chance (sources 1.2). A number that the run did not read is outside the band.
- **Two-sided.** A number beyond its band is a red gate, for better or for worse: the gate prints a table of all the numbers against the bands and names each number outside its band with the band itself.
- **In code**: the gate's cells and numbers are the package `internal/gate`, the bands are in `gate.json`. The half-width is half the 95 % interval from the same 2,000 resamples. A number that the recording did not read is recorded as "not read", and the gate holds exactly that. The gate runs `A-linked` on the pair of published maths. `sim`'s own CI holds the numbers as recorded to the bit (`just gate exact`), the callers to the bands (`just gate`). `just gate record "<reason>"` records the bands, and what they were recorded on and why is `gate.json` itself — its libraries, packages and `reason` —; the earlier recordings are the history of the file in git. The gate holds the share of items with P* below 0.50 and the share of "nothing to give": the thresholds of the CI of `modules` are taken from them, below.
- **Recording anew.** A pull request to `sim` records the bands anew, with a reason: for a chosen candidate, its report of the criterion, the decisive run and the confirmation; for a change that is not a candidate — a new pin of a package, a move, an edit of the simulator — the gate's table before and after. The new file of bands is read in review, as a snapshot is: recording turns a red gate green, and only the review sees why (sources 1.2). The bands lie in the gate file in `sim`; the runner, the gate's time, the order of releases of `sim` and of the libraries, and the gate in the CI of `modules` are the gate in CI, below.

### 3.8. Sizes of runs and seeds

- **Sizes:** a decisive run and a confirmation are 2,000 learners a cell, on 68 cells: the 65 and the three of the populations `D-`, which the engine's ceiling and the gate do not run; a rough look is fewer than 2,000 and decides nothing — the recipe `just rough <rule> <file> [learners]`, the body of `just decisive` on 300 learners a cell unless named, and only on the working learners, since held-out learners that have been looked at are held out no longer; the gate is the first 250 working learners of a population. The recipe `just decisive engine|ceiling <file> [set]` runs a decisive run — the set `working`, `held-out-<criterion>-<n>` or `held-out-<criterion>-<variant>-<n>` (below), and the candidate from `CANDIDATE_LEARNER_MODEL` and `CANDIDATE_ENGINE`: processes by parts of the learners, on all the machine's cores, then `sim merge`, with the choice anew for the first 10 learners of a cell and with a process on one processor and `GOGC` 400. Its time, with the host's load, is measurements 1.3: the sizes above were chosen by it. The files of its results do not lie in the repository — their size is in measurements 1.3 too: the same seeds and the same bits on any build give them anew to the byte, and the file of paths names their SHA-256. Between judgements they lie in `runs/` of the working copy, which `git` does not see, and a judgement runs only the candidate.
- **The working learners** — the seed 20261107, the experiment `working`. The gate and the decisive runs take the same working learners, as standalone's guard and runs do (sources 1.1).
- **The held-out learners** are each choice's own: the seed and the experiment `held-out-<criterion>-<n>`, where the criterion is `model`, `engine` or `pair`, and n is the number of the choice of that criterion. The model's first choice — the seed 20261108, the experiment `held-out-model-1`, looked at by the judgement `model-2` and no longer held out; the engine's first choice — the seed 20261109, the experiment `held-out-engine-1`, kept for the round `engine-2`. A judgement of one variant apart from the rounds of its criterion has a set of its own, `held-out-<criterion>-<variant>-<n>`: the judgement of consolidation in a lesson — the seed 20261113, the experiment `held-out-engine-lesson-1`, still held out: its judgement ended in an exit without a confirmation; the judgement of the round of fairness — the seed 20261116, the experiment `held-out-model-fair-1`. The seed of each next choice and of each pair is written down in the log before the first run of its candidate: a set that has been looked at is no longer held out, and two choices do not share one set. Which judgement confirms on which set is a table of `internal/seed`, beside the seeds: `model-2` — `held-out-model-1`, `engine-2` — `held-out-engine-1`, `engine-lesson-1` — `held-out-engine-lesson-1`, `model-fair-1` — `held-out-model-fair-1`. The entry that records a seed names its judgement, whose row comes into the table with the code that runs it — `model-3` with `held-out-model-2` —, and no set is in two rows.
- **Places** — as for the seeds of the virtual learners above: the names are the experiment, the unit, the purpose. A test of the code shows that no learner of any population is drawn alike in two sets.
- **A seed as a number** is an unsigned 64-bit integer, written in decimal digits ([format text](../spec/format/README.md)). The seeds are the dates of the day they were written down, as 20261001 and 20261003 in standalone (sources 1.2).

### 3.9. The gate in CI

How the CI of `learner-model`, `engine` and `modules` takes the gate above. The way is `go.work`, written by the caller on the fly: the runner, the gate's time and the changes it runs on live in the three repositories' own workflows.

**The gate file** lies in `sim`, beside the simulator's code, and names everything its numbers were recorded on:
- the commits of `learner-model` and `engine`, by full SHAs. A commit of a released version, or a commit of a pull request not merged yet — the order of releases below;
- the packages — the tag of the release of `modules` and the digest of its index, as the configuration of `api` pins them, and each package by the module ID, the version and the digest. By the tag the job downloads the index and its signature, `release-verify` accepts the index, and the job takes the packages by the digests from the index, from the release that their entry names;
- the versions of the shared dependencies that the workspace chose at the recording — of the Go module `spec`, and the `go` line of each module (below);
- the bands — the value and the half-width of each number of the gate.

The file is `gate.json` at the root of `sim`, JSON. The gate builds the simulator only on the commits from the file — at the callers and in its own CI too: the gate recipe of `sim`, which its gate job calls, writes `go.work` from the file into a temporary folder and points `GOWORK` at it, and does not take the versions from `go.mod`. This workspace is written by the hidden recipe `workspace`, one for the gate and for a candidate's decisive run, and `sim gate verify` holds the candidate's build before the run — the same check as the gate's, without bands. The job "Go" of the shared `go.yml` runs the tests of the simulator's code without `go.work`, on the versions from `go.mod`: there is no gate in `ci-test`. So that its jobs stay green when the file names a commit that is not in any release yet, the `go.mod` of `sim` names each library at the same point as the file: by the tag of the release, and while there is no release, by the pseudo-version of the commit. The Go proxy serves a commit by SHA, and the gate checks `go.mod` against the file. A lower bound instead would let an edit of the simulator for an API that is not in a release bring down the job "Go" until the library's release. `go.work` makes each commit from the file a main module, and a main module has no version and is taken as it is, whatever version `go.mod` requires ("MVS starts at the main modules (special vertices in the graph that have no version)", sources 2.1). So the caller runs exactly what the numbers were recorded on, except its own code.

**How a caller takes `sim`.** By a CI job of its own, not by the shared `go.yml`: that one runs the caller's recipes on the caller's own code, and has nothing to fetch `sim` and the second library with and to build them through `go.work`: its one input, `same-bits`, adds runs on other builds of the same code. The job:
1. fetches `sim` by the tag and the SHA of its commit, written in the caller's workflow: the tag for reading, the SHA as what holds the content, as with actions pinned by SHA. `sim` is taken as source from git, not as a release file, so it needs no `release-verify`; the packages of the modules, by the index from the gate file, which `release-verify` has accepted (above);
2. fetches the second library by the commit from the gate file of that tag;
3. writes `go.work` on the fly — `use` of the three modules — and does not commit it. The Go documentation advises CI not to take a `go.work` committed into a module — "CI systems should generally not be allowed to use the go.work file" (sources 2.1): the library runs its own tests without it, and the gate measures the library precisely inside the simulator;
4. builds and runs the gate in the stage `toolchain` of the devcontainer of `sim` at the same tag: Go and the tools are those on which the numbers were recorded, after the pattern of the job `go-arm64` of `learner-model`, which builds its own stage `toolchain` and runs a recipe in it.

If the caller's code breaks an API that `sim` or the second library is built on, the build fails and the gate is red. The Go documentation does not say this in words; it is an inference: `use` substitutes the code, and code that lacks an API does not compile.

**Shared dependencies.** The three modules of the workspace have one build, and for a module that several of them require MVS chooses one version — the highest required (sources 2.1). So a library in the gate may build with another version of the Go module `spec` than the tag of its submodule. Therefore the file names the chosen versions of the shared dependencies, and the gate checks the chosen ones against the recorded ones: another version is a red gate with a reason, as another commit is. Aligning them is a move of the caller or of `sim` to a tag of `spec` by a task of its own, with new bands if the numbers shifted. `learner-model` takes only Go's standard library, so for it this is only the `go` line. The gate does not change the compiler: a module's `go` line newer than the Go of the stage `toolchain` of `sim` is a red gate with a reason. The check `sim gate check` holds this: the `go` lines of the three modules equal those recorded in the file and are no newer than the Go the gate is built with.

| CI | When it runs | What is taken | What is substituted | What it holds |
|---|---|---|---|---|
| `learner-model` | every pull request and every commit of `main` | `sim` — tag and SHA; `engine` — the commit from the file; the published packages from the file | the code of `learner-model` | the invariants and the gate's numbers within the bands |
| `engine` | the same | `sim` — tag and SHA; `learner-model` — the commit from the file, whatever version the `go.mod` of `engine` requires; the packages from the file | the code of `engine` | the same |
| `modules` | a pull request where what the simulator reads from a package has changed, and a pull request that changes the tag of `sim`; none in a format transition, where `modules` changes nothing of what the simulator reads except the writing itself in the new version of the format | `sim` — tag and SHA; both libraries — by the commits from the file | the packages that the pull request built | the invariants and the thresholds below, without bands |
| `sim` | every pull request and every commit of `main` | both libraries — by the commits from the file; the packages from the file | the code of `sim` | the invariants and the gate's numbers within the bands |

The gate still runs a pull request of `engine` that raises the version of `learner-model` in its `go.mod` on the commit of `learner-model` from the file: a new pair of libraries is a change that passes through the simulator, and `sim` records it like any other.

**The gate in the CI of `modules`** judges not a library but content, and an edit of content moves the numbers by design. So it has no bands:
- **what changed.** Whether what the simulator reads has changed, `sim` itself decides: its command compares the canonical text of what the simulator would read from the server part of the pull request's package — the manifest, the graph and the tiers, the tasks, the lessons and the instances of templates, without the texts for the learner — with the same of the newest published version of the module of the same format version, as `modules` compares the graph. A new module has changed whole. So the list of what the simulator reads lives in one place — in the simulator's code;
- **learners** — the first 250 working learners of the gate's populations on the graphs of the modules that changed. `A-linked` runs if at least one of the maths changed, on the packages of both from the pull request: the CI of `modules` builds all the modules, and `sim gate changed` also gives out an unchanged module that a graph of a gate population holds together with a changed one;
- **what it holds** — the invariants `I1`–`I4` and the thresholds of the first slice, where the engine holds the corridor, does not get stuck and does not declare "mastered" too early. The thresholds are a proposal made in execution:
  - `E2` — the share of learners stuck and the share of "nothing to give" with a non-empty pool no more than on the published graphs, plus the author's tolerance, 1 percentage point: the largest value of `E2` in the gate file at the same tag of `sim`. Content must not add being stuck to what the engine already has, and the engine is judged by its criterion, where `E2` is "no more than the base's". An absolute zero would hold every pull request of `modules` red if the accepted engine gets stuck for even one learner;
  - `E1` on `G0` and `G2-half` — the issued items with P* below 0.50 no more than their largest share in the gate file on these populations plus 1 point, and the share in the corridor no less than the smallest less 1 point. Fixed thresholds — 25 % and half the pool's ceiling — were rejected: the base engine met them on the published packages in no cell, and the gate would have held every pull request red. They remain a target of the engine's criterion;
  - `M4` on `G0` — false "mastered" at most 20 %, as the floor of the model's criterion;
  - `E5` on `E-base` — not one task with a rubric that the learner has already closed;
- **in code**. The command "whether it changed" is `sim gate changed`. It compares the canonical text of the translated module, that is, exactly what `pack.Translate` takes, with the same of the newest published version that is not withdrawn. The states are `new`, `changed`, `same` and `transition`; in a format transition a module does not run, even when the pull request changes the tag of `sim` (`-all`). The mode `just gate modules` runs the gate on the packages of the pull request: the gate's cells whose graphs are wholly covered by the packages that run, with a repeat for `I1`, then `sim gate thresholds`. `A-linked` runs on both maths from the pull request: `sim gate changed` gives out the unchanged one with the line `along`, and it runs only in the cells that it shares with the changed one. The report names a module on which no population of the gate runs, and the gate does not turn red for it; in the same way it names a cell that lacked the package of the second module of its graph. The form of the call for the job of `modules` is README, "Gate in the CI of modules";
- **what next.** Merged content comes out as a release of `modules`. `sim` pins its packages by a pull request of its own, with new bands and the gate's table before and after, and the libraries take that tag when they need to.

**Time and the runner.** The gate runs on `ubuntu-24.04`: for a public repository it is x64 with 4 CPUs and 16 GB, free, and a job may run for up to 6 hours (sources 2.3). The budget of each of its jobs is `timeout-minutes` of `.github/workflows/gate.yml`. The gate's time on the runners is measurements 1.1, in the development container measurements 1.2. The gate's size is taken by the slowest measurement at each caller, with 3 minutes of margin before the timeout — `learner-model` and `engine` have no Go cache, and the gate runs longer there —, and the choice anew on the repeat is taken only for the first 10 learners of a cell. The gate's process runs with `GOGC` 400 and on one processor. A gate that does not fit is cut by an edit of `sim`, not by time.

**The same bits.** The bands do not depend on the architecture: the same bits on any build are held by `learner-model`, by the simulator's distributions and by `engine`, which promises «тот же выбор и тот же код на любой сборке одной своей версии и версии `learner-model`». So `sim`'s own CI runs the gate on `ubuntu-24.04-arm` too and checks the numbers to the last digit, and for the callers `ubuntu-24.04` is enough. The simulator's code keeps the input `same-bits: true` on the job "Go" of the shared `go.yml` (sources 5.2): with it run `targets` — the tests at `GOAMD64` v3, at v1 with `cpu.all=off`, on 386, in js/wasm and in wasip1, in `node:wasi`, each target in a job of its own, "Go / target (…)", with the check "Go / targets" after them (sources 5.3, 5.4); `fma-diff` — the assembly of each package with fusion and without it on six targets; `arm64` — the caller's `ci-test` on `ubuntu-24.04-arm`; `rules` — the rules of code by the tool of `.github` with the caller's lists. `fma-diff` and the rule `fused` hold the same bits of the distributions on all targets. The rule `math` lets into the code only the exactly defined functions of `math`, and the simulator takes `Exp`, `Log` and `Pow` with the same bits from `detmath` of `learner-model`. The code has no goroutines — the recipe of the decisive run splits it into processes by learners — and no ranging over maps. The runs on 386 and in WebAssembly the simulator does not need, but they run only the small tests of the code. The gate is not part of `ci-test`: in `targets` and the second half of `arm64` it would run `go test ./...` without `go.work` from the gate file, on the versions of `go.mod`. It runs as jobs of its own, below, on `ubuntu-24.04` and `ubuntu-24.04-arm`, in the stage `toolchain` of `sim`, and on both the numbers are checked against the bands to the last digit.

**The gate as jobs.** The job "Gate" of each architecture is the workflow `gate.yml`: four jobs, each `just gate-part <k> 4` — its part of the learners, those whose number gives k mod 4, in as many processes as the runner's processors —, and after them the check, `just gate-check`, which builds the workspace again, holds the build to the gate file, merges the parts — a part missing, repeated or of another run is refused — and holds the numbers. Its name is the gate's, "Gate / amd64" and "Gate / arm64", and it fails when a part failed. A learner comes from its seeds alone, so the numbers are those of `just gate`, which is the same run in one job. The Go cache is keyed by `go.sum` and the Dockerfile, a new pin building on the entry before it. The image of `toolchain` comes by the steps of the pinned `go.yml`, the same file `novatrail-toolchain.tar`, image and key; a push to `main` alone saves it and the Go cache, by the first part. A caller can call `gate.yml` by a tag of `sim`, with the tag and the SHA of its commit and the variable of its library, `GATE_LEARNER_MODEL` or `GATE_ENGINE`; the caller's move to it is its own.

**Releases of `sim`.** A release comes out by itself, after green CI on `main`: the next patch of the line, immutable, and GitHub signs it with an attestation of the tag, the commit and the files. The shared `release.yml` of `.github`, at the release that `.github/workflows/release.yml` pins, releases it and builds the stage `toolchain-core` alone: "without files" would hold only with a workflow of its own, as in `spec`, and the shared one requires at least one file in `dist/` (sources 5.2). So the release has one file, like the source archive of `engine`: `sim-<version>.tar.gz` — what builds the simulator and runs the gate, signed without a key; `release-verify` accepts it. The line is `RELEASE_LINE` of the same file. A new release comes only from a change of what the gate is built from, the input `paths` of that file. The callers take `sim` from git by tag and SHA (above), not as the archive. The callers' tag is raised by the session of a library or of `modules` — in the pull request that needs the new tag, or by a task of its own. Dependabot will not raise it: it updates references to actions and to reusable workflows of the form `actions/checkout@<commit>` (sources 2.3), and the tag and the SHA of `sim` at a caller are inputs of the checkout step, not such a reference. This is an inference from the documentation, not its words.

**The order of releases.**
- **A change breaks an API that `sim` is built on.** The library's pull request P is red: `sim` does not build.
  1. A pull request to `sim` edits the simulator's code for P, and the gate file names the last commit of P. Its CI builds the simulator on that commit, through `go.work` from the file; if the numbers did not shift, the bands stay as they were.
  2. Merge, and a tag of `sim` comes out.
  3. P raises the tag and the SHA of `sim` and turns green, then merge.
  4. The library's release comes out.
  5. A pull request to `sim` moves the file to the commit of the release, and `go.mod` to the release itself; the numbers are the same. The next tag comes out.
- **A change of `learner-model` breaks an API that `engine` is built on.** The simulator will not help here: the fix has to be a commit Q of `engine`. This is a pair, and it goes by the order of a pair below, with P and Q.
- **A change moves the numbers on purpose.** This is a candidate, and the criterion judges it: `sim` runs the decisive run and the confirmation on the last commit of P. Then the same steps: a pull request to `sim` records the bands anew, with the reason and the report of the criterion, in review, → a tag of `sim` → P raises the tag → merge → the library's release → the `go.mod` of `sim`. A change of a library that is not a candidate but moves the numbers is the same, with the gate's table before and after.
- **A pair — the threshold "mastered" and the target of the corridor**.
  1. `sim` runs the pair — the last commits P of `learner-model` and Q of `engine` — against the pair of bases. A pull request to `sim` records the bands on both commits, and a tag comes out.
  2. P raises the tag: its gate takes `engine` by the commit Q from the file and turns green. Merge of P, then the release of `learner-model`.
  3. Q raises the tag, and `learner-model` in `go.mod` to that release. Its gate takes `learner-model` by the commit P from the file and turns green. Merge of Q, then the release of `engine`.
  4. `sim` moves the file and `go.mod` to both releases.

  Between steps 2 and 3 `learner-model` has already come out, and `engine` not yet, so the pair is not merged at once. Therefore P is merged only when Q has passed review and its gate at the same tag is green, and `api` moves to both versions together — the review of the pull request of `api` holds this, as with `tutor` and `modules`. If Q is still not merged after the merge of P, `learner-model` rolls back only forward: a new pull request returns the former constant, and `sim` writes the file back to the pair of bases (Т-19).
- **A change of `sim` itself** — a new pin of a package, a population, an edit of the simulator — goes as a pull request to `sim`, with the gate's table before and after if the numbers shifted. The callers stay on the former tag, and it is still green for them: the tag is immutable.
- **A change of content** — the gate of `modules` above, and after the release a new pin in `sim`.

A pull request P that got new commits after the bands were recorded passes the gate if the numbers on its code are the same: the gate checks the numbers, not the commit. If P is closed without a merge, the tag of `sim` recorded on it stays, and the next pull request to `sim` returns the file to the released version. Until the library comes out, the file names a commit that is not in its releases. This is an interim tag, and the callers take it only in the steps above.
